## Логическая копия и восстановление в новую БД

**Средний уровень.** Полный рецепт оболочки для данных из [queries.sql](queries.md#полный-пример-учебная-база).
Исходная БД — `cheatsheet_demo`; целевой БД `cheatsheet_restore_check` ещё нет.
Роль postgres здесь относится к изолированному учебному серверу; в рабочем окружении нужны
отдельные права и регламент. Пароль вводится по запросу или берётся из настроенного password file.

Рецепт создаёт каталог резервной копии и новую БД. Исходник не удаляется, существующая целевая БД
не перезаписывается: createdb остановит сценарий, если имя занято. Команды выполняются в одной оболочке.

```bash
set -eu
backup_dir="$(mktemp -d)"

pg_dump --host=127.0.0.1 --username=postgres --dbname=cheatsheet_demo \
  --format=custom --file="$backup_dir/cheatsheet_demo.dump"

pg_restore --list "$backup_dir/cheatsheet_demo.dump"

createdb --host=127.0.0.1 --username=postgres --template=template0 cheatsheet_restore_check

pg_restore --host=127.0.0.1 --username=postgres --dbname=cheatsheet_restore_check \
  --single-transaction --exit-on-error --no-owner --no-privileges \
  "$backup_dir/cheatsheet_demo.dump"

psql --host=127.0.0.1 --username=postgres --dbname=cheatsheet_restore_check \
  --no-psqlrc --set=ON_ERROR_STOP=1 --command="SELECT
    (SELECT count(*) FROM demo.users) AS users,
    (SELECT count(*) FROM demo.products) AS products,
    (SELECT count(*) FROM demo.orders) AS orders,
    (SELECT stock FROM demo.products WHERE id = 1) AS keyboard_stock;"

printf 'Архив: %s\n' "$backup_dir/cheatsheet_demo.dump"
```

**Ожидаемый результат:** pg_restore завершится без ошибок; проверка даст
`users = 3`, `products = 3`, `orders = 3`, `keyboard_stock = 10`.
Проверка предполагает неизменённые учебные данные; для своей БД нужны проверки её инвариантов,
приложения, ограничений и полноты объектов, а не только подсчёт строк.

`--no-owner --no-privileges` удобны для учебного восстановления под текущим владельцем:
исходные владельцы и ACL **не восстанавливаются**. Это не полная репетиция переноса прав рабочей БД.
`--single-transaction` откатывает восстановление при ошибке; для большого restore это может быть неудобно,
и этот режим не совмещают с параллельным `--jobs`.

Не добавляйте `--clean` ради устранения ошибки: он удаляет существующие целевые объекты.
Копии содержат данные и требуют подходящих прав доступа/хранения. Восстанавливайте только доверенный
дамп: восстановление выполняет SQL и может исполнить код, выбранный владельцами исходного сервера.

Очистка необязательна: сначала сохраните нужный архив. Команда оболочки ниже **удалит всю проверочную БД**;
выполняйте только после проверки имени и закрытия её соединений:

```bash
dropdb --host=127.0.0.1 --username=postgres cheatsheet_restore_check
```

## Другие форматы и границы копии

**Средний уровень.** Это справка по параметрам, не дополнительный сценарий изменения БД:

| Задача | Параметры / инструмент | Условие |
| --- | --- | --- |
| Обычный SQL-файл | `pg_dump --format=plain --file=backup.sql` | Восстановление через psql, а не pg_restore; целевая БД создаётся отдельно |
| Сжатый архив | `pg_dump --format=custom` | Выбор объектов и восстановление через pg_restore |
| Параллельный dump | `pg_dump --format=directory --jobs=4` | Только directory; число потоков подбирают по ресурсам |
| Параллельный restore | `pg_restore --jobs=4` | Custom/directory, без single-transaction; предварительно планируют ресурсы и обработку ошибок |
| Только схема / данные | `--schema-only` / `--data-only` | Данные без схемы требуют заранее совместимой структуры |
| Только отдельные таблицы | `--table=demo.orders` | Зависимые объекты не обязательно включатся автоматически |
| Роли и tablespaces кластера | `pg_dumpall --globals-only` | Отдельный административный экспорт; файл может содержать хеши паролей и требует защиты |

pg_dump делает согласованный логический снимок одной БД; глобальные роли и tablespaces в него не входят.
Используйте клиентские утилиты целевой ветки и сверяйте совместимость: pg_dump не читает сервер
более нового major, чем он сам; восстановление в более старый major не гарантируется.
Для обычного SQL-файла включайте `psql --no-psqlrc --set=ON_ERROR_STOP=1`;
если нужен единый откат, заранее проверьте, допускает ли содержимое выполнение одной транзакцией.

## PITR и репликация

**Продвинутый уровень. Концептуальный маршрут, не готовый сценарий для production.**
PITR восстанавливает кластер из физической базовой копии и непрерывной последовательности WAL.
pg_dump не является базовой копией для PITR. До настройки определите допустимые потери данных,
время восстановления, хранение, доступ и регулярный тест на отдельном сервере.

1. Настройте и проверьте доставку WAL в независимое хранилище: сохранение при повторе,
   правильные коды завершения, контроль пропусков, места и сроков хранения.
2. Получите физическую базовую копию, например pg_basebackup, с нужными правами и WAL.
   Сохраните конфигурацию, версии, tablespaces и ключи доступа отдельно по регламенту.
3. Для тренировки остановите **отдельный целевой** экземпляр, восстановите совместимую базовую копию
   в его data directory и обеспечьте доступ к цепочке WAL с начала копии до цели.
4. Задайте restore_command и одну цель восстановления, например recovery_target_time с явной зоной;
   настройте действие при достижении цели. Параметры задаются в обычной конфигурации PostgreSQL 18.
5. Создайте `recovery.signal` в целевом data directory и запускайте целевой экземпляр по документации.
   Проверьте логи, достигнутую точку и данные; решение о завершении recovery/promotion принимается отдельно.

`recovery.conf` удалён из PostgreSQL начиная с 12: наличие такого файла препятствует запуску.
Для standby используется `standby.signal`, а не recovery.signal как взаимозаменяемая настройка.
Физическая репликация также опирается на base backup/WAL, но реплика сама по себе не заменяет backup:
ошибочное удаление может попасть и на неё. Слот репликации может удерживать WAL и заполнить диск,
если потребитель отстал; нужны наблюдение и ограничения хранения.

Здесь намеренно нет универсального `archive_command = 'cp ...'`: надёжность копирования,
повторы, конфликт имён, права, удалённое хранилище и восстановление проверяются в конкретном окружении.
Практическую настройку выполняют по [процедуре PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)
и [pg_basebackup](https://www.postgresql.org/docs/18/app-pgbasebackup.html).
