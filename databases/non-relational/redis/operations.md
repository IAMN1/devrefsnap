## Учебный экземпляр

Все Python-примеры используют обязательный REDIS_URL и случайный namespace `cheatsheet:{id}:`.
Удаляются только явно созданные ключи; FLUSHDB/FLUSHALL не нужны.
Выполняйте их на выделенном процессе с синтетическими данными, а не на работающем системном сервисе.

Вариант локальной подготовки после установки Redis: в отдельном терминале создайте временный каталог
и запустите процесс в foreground с Unix socket, без TCP и persistence. Это полный пример оболочки;
он создаёт временные файлы, но не меняет настройки системной службы:

```bash
umask 077
redis_demo_dir="$(mktemp -d)"
printf 'Сокет учебного процесса: %s/redis.sock\n' "$redis_demo_dir"
redis-server --port 0 --unixsocket "$redis_demo_dir/redis.sock" --unixsocketperm 700 \
  --save "" --appendonly no --dir "$redis_demo_dir"
```

Дождитесь готовности процесса. В другом терминале задайте REDIS_URL с **выведенным** путём:
форма — `unix:///полный/путь/redis.sock?db=0`. Не копируйте условный путь буквально.
Проверьте PING, например через `redis-cli -s /полный/путь/redis.sock PING`; ожидается PONG.
После завершения своих опытов остановите только этот foreground-процесс через Ctrl-C.
Persistence отключён: его данные исчезнут при остановке. Пример не является настройкой production.

## Сохранность и восстановление

| Механизм | Назначение | Что проверить |
| --- | --- | --- |
| RDB | Снимок состояния | Потеря изменений после последнего снимка; ресурсы fork/диска; восстановление файла на отдельном процессе |
| AOF | Журнал записей | appendfsync, ошибки диска, rewrite и multi-part AOF; при everysec возможна потеря примерно последней секунды при сбое |
| RDB + AOF | Совмещение способов | Что сервер загрузит при старте и как копируются все необходимые файлы |
| Репликация | Копия для чтения/доступности | Обычно асинхронна; failover может потерять подтверждённые записи |
| Backup вне экземпляра | Восстановление после удаления/аварии | Отдельное хранение, доступ, retention и регулярная проверка восстановления |

MULTI/EXEC не включает автоматически AOF/fsync. WAIT позволяет ждать подтверждений реплик,
но не превращает систему в строго согласованное хранилище с гарантией отсутствия потери записи при любых отказах.
Реплика повторяет также ошибочные удаления: она не заменяет независимый backup.
Нельзя считать копию пригодной только потому, что файл существует: восстановите её на отдельном экземпляре
с совместимой версией и проверьте прикладные данные.

## Память и наблюдение

Задайте maxmemory с запасом для служебных расходов/persistence/репликации и политику eviction под задачу.
noeviction отклоняет часть записей при нехватке памяти; allkeys-lru/lfu вытесняют ключи,
volatile-политики выбирают только ключи со сроком. TTL и eviction — разные причины исчезновения.
Большие значения и команды с большим результатом увеличивают задержки; pipeline нужно ограничивать по размеру.

Справочные команды Redis, не настройки для копирования целиком:

```text
INFO server
INFO memory
INFO persistence
INFO replication
INFO stats
SLOWLOG GET 5
LATENCY DOCTOR
```

Смотрите evicted_keys, expired_keys, попадания/промахи кеша, задержки, память, состояние AOF/RDB
и отставание реплик. Часть диагностики требует прав и предварительной настройки;
SLOWLOG может содержать аргументы команд, поэтому доступ к нему ограничивают.
UNLINK откладывает освобождение памяти значения; это не отменяет удаление ключа.

## Репликация, Sentinel и Cluster

Sentinel наблюдает за репликацией и организует failover, а не шардирует данные.
Redis Cluster распределяет ключи по 16384 hash slots и требует клиента с поддержкой перенаправлений.
Hash tag в фигурных скобках позволяет совместно разместить связанные ключи;
многоключевые операции/транзакции обычно требуют одного slot.
Cluster использует БД 0; SELECT не разделяет арендаторов на разные cluster-БД.
Разбиение одного большого/горячего ключа автоматически не происходит от добавления shard.

## Доступ и безопасность

Ограничьте сеть и доступ к socket; protected mode не заменяет продуманные ACL.
В рабочем окружении используйте отдельные ACL users, минимальные категории команд и шаблоны ключей/каналов.
AUTH без TLS не шифрует сеть; для удалённого доступа нужны соответствующие TLS и проверка сертификата.
Секреты не помещают в публикуемые URL/команды/логи.
Административные CONFIG/DEBUG/SHUTDOWN/FLUSH* и чтение чужих ключей не нужны приложению кеша.
Не используйте просто номер логической БД как границу безопасности.
