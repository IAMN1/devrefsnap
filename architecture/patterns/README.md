# Паттерны проектирования и архитектуры

Паттерн описывает повторяющуюся проблему, решение и цену его применения.
Названия помогают обсуждать устройство кода; наличие паттерна не является целью проекта.

## Базовый уровень

Начните с проблемы и простой функции. Strategy в Python может быть callable,
Adapter — функцией преобразования, Factory — обычной функцией сборки.
[Паттерны кода](design-patterns.md) не требуют автоматически создавать иерархию классов.

## Средний уровень

Сравните альтернативы на реальном сценарии изменения: какие знания скрыты, какой контракт появился,
как проверить успешный результат и отказ. Layered и Vertical Slice описывают разные акценты
[организации кода](architecture-patterns.md); детали можно комбинировать с явными границами.

## Продвинутый уровень

Перед разделением на процессы определите владение данными, возможные отказы и протокол повтора.
[Outbox/Saga/CQRS](architecture-patterns.md) добавляют состояние и обязанности сопровождения;
они не обещают exactly-once для произвольного внешнего эффекта.

## Частые ошибки

| Смешение | Уточнение |
| --- | --- |
| Ports & Adapters = microservices | Первое — границы приложения/адаптеров, второе — независимые сервисы и развёртывания |
| Python @decorator = любой Decorator pattern | Синтаксическая обёртка функции и объектный паттерн связаны по идее, но не тождественны |
| Factory = обязательно Abstract Factory / Factory Method | Простая функция создания не обязана реализовывать более сложный GoF-паттерн |
| CQRS = Event Sourcing | Разделение моделей чтения/записи не требует журнала событий как источника истины |
| Retry = повторять любую ошибку | Нужны классификация отказа, ограничение попыток/времени и идемпотентность |
