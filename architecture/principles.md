# Принципы проектирования

Принципы помогают выбирать границы и проверять изменения. Они не определяют число классов,
слоёв или сервисов: решение оценивают по конкретным требованиям и последствиям.

[К архитектуре](README.md) · [SOLID](solid.md) · [Паттерны](patterns/README.md)

| Параметр | Значение |
| --- | --- |
| Предпосылки | Функции, модули, состояния и тесты; примеры на Python 3.14 |
| Концепции сверены | 2026-11-06, первичные источники внизу; это обзор, не проверка архитектуры конкретного проекта |
| Выполнено | 2026-11-06, Python 3.14.7: полный пример; успешный резерв, три отказа без изменения состояния и отказ недопустимого начального остатка |
| Границы | Пример проверяет локальный контракт в памяти; не конкуренцию, сеть или эксплуатационные свойства |

## Быстрый поиск

| Наблюдение | Что рассмотреть | Проверка |
| --- | --- | --- |
| Одно изменение затрагивает несвязанные задачи | Cohesion / coupling | Какие правила действительно меняются вместе? |
| Внешний код изменяет поля в обход правил | Инкапсуляция / инварианты | Можно ли получить недопустимое состояние через публичный API? |
| Одно бизнес-правило скопировано в нескольких местах | DRY | Будет ли изменение этого знания требовать синхронных исправлений? |
| Появился универсальный каркас без потребителя | KISS / YAGNI | Какая текущая задача и проверка требуют этой сложности? |
| Тест правила требует запуска внешней службы | Граница зависимости | Можно ли отделить правило от адаптера с сохранением контракта? |
| Обсуждение застряло на названиях паттернов | Компромисс / эксперимент | Какой сценарий должен стать проще и что станет дороже? |

## Базовый уровень

### Связность и связанность

**Cohesion, внутренняя связность:** модуль объединяет знание и действия, которые нужны для одной
согласованной задачи и меняются по связанным причинам. **Coupling, связанность:** сколько предположений
одна часть делает о другой — её данных, порядке вызовов, протоколе ошибок или времени ответа.

Практический ход: возьмите реальное изменение и перечислите затронутые правила.
Объединяйте совместно меняющееся знание; отделяйте детали, которые меняются независимо.
Много файлов само по себе не уменьшает связанность: общая изменяемая структура может связать их сильнее явного вызова.

### Контракт и инвариант

Контракт описывает допустимый вход, результат, ошибки и побочные эффекты.
Инвариант — свойство допустимого состояния, которое операции должны сохранять.
Например, остаток неотрицателен, резервируется положительное количество, а отказ не уменьшает остаток.

Полный пример. Сохраните как `invariants.py`, выполните `python3.14 invariants.py`; зависимостей нет.

<!-- example: architecture/invariants.py -->
```python
class OutOfStock(Exception):
    pass


class Stock:
    def __init__(self, available: int):
        if type(available) is not int or available < 0:
            raise ValueError("Остаток должен быть целым неотрицательным числом")
        self._available = available

    @property
    def available(self) -> int:
        return self._available

    def reserve(self, quantity: int) -> None:
        if type(quantity) is not int or quantity <= 0:
            raise ValueError("Нужно целое положительное количество")
        if quantity > self._available:
            raise OutOfStock(quantity)
        self._available -= quantity


stock = Stock(3)
stock.reserve(2)
assert stock.available == 1
for quantity, expected in [(0, ValueError), (True, ValueError), (2, OutOfStock)]:
    before = stock.available
    try:
        stock.reserve(quantity)
    except expected:
        pass
    else:
        raise AssertionError("Ожидался отказ контракта")
    assert stock.available == before
try:
    Stock(-1)
except ValueError:
    pass
else:
    raise AssertionError("Недопустимое начальное состояние")
print("OK: successful reservation, invariant and unchanged state on refusal")
```

**Результат:** OK. Проверены успех, неверный вход, нехватка и отсутствие изменения при отказе.
В Python `_available` — соглашение о внутреннем API, а не защита от намеренного доступа.
Пример однопоточный; атомарность конкурентного резерва в БД потребует отдельного протокола/транзакции.

## Средний уровень

### Инкапсуляция и зависимости

Скрывайте решение, которое потребителю не нужно знать: способ хранения, формат внешнего SDK,
внутренний индекс. Возвращаемая наружу изменяемая коллекция может открыть обход инварианта;
выбирайте копию, неизменяемое представление или явную операцию по требованиям.

Граница полезна, если позволяет изменить деталь без переписывания правила и проверить договорённость.
Функция-параметр, модуль или небольшой Protocol могут быть достаточны; интерфейс на каждый класс не обязателен.
См. [DIP и DI](solid.md#продвинутый-уровень) и [Ports & Adapters](patterns/architecture-patterns.md#организация-кода).

### DRY, KISS и YAGNI

| Принцип | Действие | Когда не спешить |
| --- | --- | --- |
| DRY | Сделать одно бизнес-знание авторитетным в одном месте | Похожие строки могут выражать независимые правила и расходиться дальше |
| KISS | Выбрать понятное решение, достаточное для текущего контракта | «Короче» не обязательно проще: скрытые режимы и неявные побочные эффекты усложняют чтение |
| YAGNI | Отложить предполагаемую возможность без подтверждённой потребности | Это не отказ от тестов, понятных границ и работы, необходимой для текущих требований |

Пример решения: два отчёта пока случайно имеют одинаковые столбцы, но ими управляют разные требования.
Можно оставить форматирование рядом с каждым отчётом. Когда появится общее правило формата,
выделить его и проверить обоих потребителей. Общий helper с множеством флагов способен увеличить связанность.

## Продвинутый уровень

### Делать компромисс проверяемым

Перед существенным разделением модуля зафиксируйте короткую запись, а не псевдоконфигурацию:

| Поле решения | Пример конкретной записи |
| --- | --- |
| Наблюдаемая проблема | Добавление нового перевозчика требует менять расчёт корзины и обработку HTTP-ошибок в одном модуле |
| Ограничение | Цена должна рассчитываться без сети в тестах; существующие результаты не меняются |
| Пробное изменение | Вынести перевод ответа перевозчика в адаптер; оставить правило выбора тарифа отдельной функцией |
| Проверка | Старые контрактные тесты проходят для обоих адаптеров; HTTP-модуль не импортируется расчётом |
| Цена | Появляется контракт ошибок и место сборки объектов; его тоже нужно сопровождать |
| Когда пересмотреть | Сменился контракт тарификации либо адаптеры всё равно требуют подробностей SDK внутри правила |

Изоляция данных, доступность, задержка и сложность согласованности могут конфликтовать.
Договоритесь, какое свойство приоритетно в конкретном сценарии и как наблюдать нарушение.
Ни число слоёв, ни процент покрытия сами по себе не доказывают хорошую границу.

### Менять контракт постепенно

Для опубликованного интерфейса рассмотрите parallel change: сначала добавить совместимый путь,
потом перевести и проверить потребителей, затем удалить старый. Период совместимости имеет стоимость;
заранее определите, как подтвердить отсутствие старых обращений. Для внутренней локальной функции
одновременное изменение всех вызовов может быть проще и безопаснее.

## Частые ошибки

| Ошибка | Более полезная проверка |
| --- | --- |
| «DRY требует убрать любое совпадение» | Это одно знание или временно похожий текст? |
| «Абстракция нужна на будущее» | Есть ли текущий вариант изменения и потребитель? |
| «Инкапсуляция — только private-поля» | Сохраняют ли публичные операции инварианты и контролируют ли побочные эффекты? |
| «Микросервисы исправят связанность» | Можно ли менять/выпускать части независимо, или связанность станет сетевой? |
| «Тест примера доказал архитектуру» | Он проверил только названные входы и состояния; нагрузка и отказы проверяются отдельно |
