## 1. Что такое Pull Request? {#что-такое-pull-request}

**Pull Request (PR)** – это основной инструмент collaboration в Git, который позволяет:
- **Ревью кода** перед слиянием изменений
- **Обсуждение** предлагаемых изменений
- **Автоматическое тестирование** через CI/CD пайплайны
- **Документирование** причин изменений

**Ключевая терминология:**
- **Базовая ветка (base branch)** – целевая ветка (обычно `main`, `master`)
- **Ветка сравнения (compare/head branch)** – исходная ветка с вашими изменениями
- **Слияние (merge)** – интеграция изменений из одной ветки в другую
- **Сквош (squash)** – объединение нескольких коммитов в один
- **Перебазирование (rebase)** – переприменение коммитов поверх другой базы

## 2. Зачем использовать Pull Requests? {#зачем-использовать-pull-requests}

### ✅ Преимущества:
- **Качество кода** – раннее обнаружение багов через ревью коллег
- **Обмен знаниями** – команда узнает об изменениях в кодовой базе
- **Документирование** – описания PR объясняют «почему», а не только «что»
- **Безопасность** – предотвращает поломку основной ветки
- **Контроль процесса** – формализует процесс управления изменениями

### 📊 Когда создавать PR:
- Добавление новых функций
- Исправление багов
- Рефакторинг кода
- Обновление зависимостей
- Любые изменения, которые должны быть проверены

## 3. Стратегии ветвления {#стратегии-ветвления}

### Стратегия 1: Feature Branch Workflow (Рекомендуется)
```
main (всегда готов к деплою)
  │
  ├── feature/login-ui (короткоживущая, 1-3 дня)
  ├── feature/api-auth (короткоживущая, 2-5 дня)
  └── feature/payment (короткоживущая, 3-7 дней)
```

### Стратегия 2: GitFlow (для сложных проектов)
```
main (продакшн)
  │
develop (интеграция)
  │
  ├── feature/*
  ├── release/*
  └── hotfix/*
```

### Стратегия 3: Длинные ветки (Long-Running Branches)
```
main
  │
dev (длинная ветка, WIP)
  │
  └── feature/* (ветки от dev)
```

## 4. Создание идеального PR {#создание-идеального-pr}

### Пошаговое создание:

1. **Подготовьте ветку:**
```bash
# Начните с обновленной main
git checkout main
git pull origin main

# Создайте feature-ветку
git checkout -b feature/описание-фичи

# Внесите изменения, коммит
git add .
git commit -m "feat: добавляет компонент профиля пользователя"
```

2. **Запушьте в удаленный репозиторий:**
```bash
git push origin feature/описание-фичи
```

3. **Создайте PR на GitHub:**
   - Нажмите "Compare & pull request"
   - Установите base: `main`, compare: `ваша-ветка`
   - Напишите описательный заголовок и описание

### 📝 Шаблон описания PR:
```markdown
## Что делает этот PR?
Кратко опишите цель этого изменения.

## Тип изменения
- [ ] Исправление бага
- [ ] Новая функциональность
- [ ] Критическое изменение (breaking change)
- [ ] Обновление документации

## Изменения
- Перечислите конкретные изменения
- Маркированный список полезен
- Включите технические решения

## Тестирование
- [ ] Юнит-тесты добавлены/обновлены
- [ ] Интеграционные тесты проходят
- [ ] Шаги для ручного тестирования:
  1. Шаг первый
  2. Шаг второй

## Скриншоты (если изменения UI)
До | После
:---:|:---:
**старое** | **новое**

## Чек-лист
- [ ] Код следует стилю проекта
- [ ] Я проверил свой код самостоятельно
- [ ] Добавлены комментарии к сложному коду
- [ ] Документация обновлена

## Связанные задачи
Closes #123, Fixes #456
```

## 5. Процесс ревью PR {#процесс-ревью-pr}

### Как автор:
1. **Сначала саморевью** своего кода
2. **Добавьте ревьюверов** (2+ для критических изменений)
3. **Отвечайте на комментарии** оперативно
4. **Вносите изменения** и пушите обновления
5. **Запросите повторное ревью** когда готово

### Как ревьювер:
1. **Сначала прочтите описание PR**
2. **Ревьюьте код, а не человека**
3. **Будьте конкретны** в обратной связи
4. **Предлагайте решения**, а не только указывайте на проблемы
5. **Аппрувьте**, когда критерии выполнены

### Чек-лист для ревью:
- [ ] Код решает заявленную проблему
- [ ] Нет очевидных багов или краевых случаев
- [ ] Следует конвенциям проекта
- [ ] Тесты адекватны
- [ ] Документация обновлена при необходимости
- [ ] Учтена производительность
- [ ] Рассмотрены последствия для безопасности

## 6. Стратегии слияния {#стратегии-слияния}

### Вариант 1: Merge Commit (По умолчанию)
```bash
# Создает коммит слияния
git merge --no-ff feature/ветка
```
**Лучше для:** Сохранения полной истории, командной работы

### Вариант 2: Squash and Merge
```bash
# Объединяет все коммиты PR в один
git merge --squash feature/ветка
```
**Лучше для:** Поддержания чистой истории main, маленьких PR

### Вариант 3: Rebase and Merge
```bash
# Линейная история, переприменяет коммиты
git rebase main
git merge
```
**Лучше для:** Линейной истории, solo-проектов

### Сравнительная таблица:
| Стратегия | История | Количество коммитов | Лучше для |
|-----------|---------|-------------------|-----------|
| **Merge** | Ветка сохраняется | Несколько коммитов | Командные проекты |
| **Squash** | Линейная, чистая | Один коммит | Небольшие фичи |
| **Rebase** | Линейная, детальная | Несколько коммитов | Solo/мейнтейнеры |

## 7. Работа с длинными ветками {#работа-с-длинными-ветками}

### Ежедневный процесс синхронизации:
```bash
# Утренняя синхронизация
git checkout dev
git fetch origin main
git merge origin/main  # или git rebase origin/main

# Решите конфликты, если есть
git push origin dev  # или --force-with-lease если делали rebase

# Работа в течение дня
git add .
git commit -m "feat: работа в процессе"
git push origin dev

# Вечерняя синхронизация (перед завершением)
git fetch origin main
git merge origin/main
git push origin dev
```

### Поддержание актуальности feature-веток:
```bash
# Из вашей feature-ветки
git checkout feature/ваша-фича
git fetch origin main
git rebase origin/main

# Решите конфликты
git push origin feature/ваша-фича --force-with-lease
```

## 8. Решение распространенных проблем {#решение-распространенных-проблем}

### Проблема 1: Ветка отстает от Main
```
Behind: 6 | Ahead: 2
```
**Решение:**
```bash
git checkout ваша-ветка
git fetch origin main
git merge origin/main  # или rebase
# Решите конфликты
git push origin ваша-ветка
```

### Проблема 2: Нужен force push
**После rebase или amend коммита:**
```bash
# Безопасный force push
git push origin имя-ветки --force-with-lease

# Обычный force push (используйте осторожно)
git push origin имя-ветки --force
```

### Проблема 3: Конфликты слияния
```bash
# Во время merge/rebase Git показывает файлы с конфликтами
# Отредактируйте файлы для разрешения конфликтов
git add resolved-file.js
git commit -m "fix: разрешить конфликты слияния"
# или для rebase:
git rebase --continue
```

### Проблема 4: PR показывает не те коммиты
**После force push, обновите PR вручную:**
1. Отредактируйте заголовок/описание PR в интерфейсе GitHub
2. PR не обновляется автоматически после изменения истории
3. Добавьте комментарий, объясняющий force push

### Проблема 5: Не могу запушить после amend
```bash
# Вы изменили коммит, который уже был запушен
git push origin имя-ветки --force-with-lease
# Всегда сообщайте команде о force push
```

## 9. Чек-лист лучших практик {#чек-лист-лучших-практик}

### Перед созданием PR:
- [ ] Ветка обновлена относительно базовой ветки
- [ ] Код следует конвенциям проекта
- [ ] Тесты проходят локально
- [ ] Не осталось отладочного кода
- [ ] Сообщения коммитов понятны

### Создание PR:
- [ ] Описательный заголовок (feat/fix/chore: что)
- [ ] Детальное описание с контекстом
- [ ] Привязано к соответствующим задачам (issues)
- [ ] Добавлены соответствующие метки (labels)
- [ ] Назначены ревьюверы

### Во время ревью:
- [ ] Отвечайте на комментарии в течение 24 часов
- [ ] Вносите запрошенные изменения или обсуждайте
- [ ] Держите PR обновленным относительно базовой ветки
- [ ] Не добавляйте несвязанные изменения

### Перед слиянием:
- [ ] Все проверки пройдены (CI/CD)
- [ ] Получены необходимые аппрувы
- [ ] Нет конфликтов слияния
- [ ] Выбрана правильная стратегия слияния

### После слияния:
- [ ] Удалите удаленную feature-ветку
- [ ] Удалите локальную feature-ветку
- [ ] Обновите локальную ветку main
- [ ] Проверьте деплой, если применимо

## 10. Полезные команды Git {#полезные-команды-git}

### Управление ветками:
```bash
# Создать и переключиться
git checkout -b feature/имя

# Список веток
git branch -a

# Удалить ветку
git branch -d имя-ветки  # локально
git push origin --delete имя-ветки  # удаленно

# Переименовать ветку
git branch -m новое-имя
```

### Синхронизация и обновление:
```bash
# Получить последние изменения без слияния
git fetch origin

# Обновить текущую ветку
git pull origin имя-ветки

# Обновить main локально
git checkout main
git pull origin main

# Посмотреть различия
git log origin/main..ваша-ветка  # ваши коммиты
git log ваша-ветка..origin/main  # отсутствующие коммиты
```

### Управление коммитами:
```bash
# Изменить последний коммит
git commit --amend -m "новое сообщение"

# Интерактивный rebase (последние 3 коммита)
git rebase -i HEAD~3

# Сквошить несколько коммитов
# В интерактивном rebase: измените "pick" на "squash"

# Отменить последний коммит (сохранить изменения)
git reset --soft HEAD~1

# Отменить последний коммит (удалить изменения)
git reset --hard HEAD~1
```

### Команды, связанные с PR:
```bash
# Посмотреть PR из командной строки (с помощью gh CLI)
gh pr create --title "feat: что-то" --body "описание"

# Переключиться на PR локально
gh pr checkout 123

# Посмотреть статус PR
gh pr view

# Список открытых PR
gh pr list
```

### Решение проблем:
```bash
# Посмотреть статус ветки
git status

# Визуальная история
git log --oneline --graph --all -20

# Проверить ahead/behind
git rev-list --left-right --count main...feature/ветка

# Восстановить потерянные коммиты
git reflog  # затем git reset --hard <хэш-коммита>

# Очистить локальные ветки
git fetch -p && git branch -vv | grep ': gone]' | awk '{print $1}' | xargs git branch -D
```

## 📚 Быстрый справочник {#быстрый-справочник}

### Состояния PR:
- **Draft**: В процессе, не готово для ревью
- **Open**: Готово для ревью и обсуждения
- **Approved**: Готово к слиянию
- **Merged**: Успешно интегрировано
- **Closed**: Не слито (отклонено или заброшено)

### Конвенция сообщений коммитов:
```
тип(область): описание

feat: новая функциональность
fix: исправление бага
docs: документация
style: форматирование
refactor: рефакторинг кода
test: добавление тестов
chore: обслуживание
```

### Метки (labels) PR на GitHub:
- `bug` – исправление дефекта
- `enhancement` – новая функциональность
- `documentation` – изменения в документации
- `question` – требуется уточнение
- `wontfix` – не будет исправлено
- `duplicate` – уже существует

## 🎯 Итоговые советы {#итоговые-советы}

1. **Маленькие PR лучше больших** – идеально до 400 строк
2. **Одна задача на PR** – не смешивайте фичи и исправления
3. **Описывайте "почему", а не только "что"** – контекст критически важен
4. **Сначала ревьюьте свой код самостоятельно** – исправьте очевидные проблемы
5. **Синхронизируйтесь часто** – избегайте огромных конфликтов слияния
6. **Используйте Draft PR** – для ранней обратной связи по WIP
7. **Удаляйте слитые ветки** – поддерживайте репозиторий в чистоте
8. **Изучите горячие клавиши** – GitHub поддерживает многие
