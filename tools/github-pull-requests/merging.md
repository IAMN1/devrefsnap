# Синхронизация, слияние и очистка веток

Откройте страницу, чтобы обновить feature-ветку, выбрать merge method и сохранить результат перед удалением ветки.
До слияния проверьте требования GitHub и полномочия на выбранный PR.

| Задача | Приём | Пример |
| --- | --- | --- |
| Получить изменения main без потери коммитов | Fetch, сравнение и merge | [Синхронизация](#обновить-свою-ветку) |
| Выбрать итоговую историю | Merge / Squash / Rebase по требованиям | [Таблица решений](#выбрать-способ-слияния) |
| Удалить ветку после интеграции | Проверить PR, опубликованный результат и локальные коммиты | [Очистка](#проверить-результат-и-удалить-ненужную-ветку) |
| Найти причину лишних коммитов | Base/head, merge-base и ahead/behind | [Диагностика](#разобраться-с-неправильным-списком-коммитов) |

Уровень: средний и продвинутый.
Предпосылки: merge/rebase в Git и права на целевой репозиторий.

## Обновить свою ветку

**Ситуация:** `feature/profile` и серверная `main` изменились независимо; коммиты feature нужно сохранить.
Получите известное состояние сервера и слейте `origin/main` в feature.
Фрагмент предназначен для существующего проекта.
Сначала сохраните локальную работу.
Проверьте текущую ветку.

```text
git switch feature/profile
git fetch origin
git log --oneline --left-right HEAD...origin/main
git merge origin/main
```

**Результат без конфликта:** при расхождении merge создаёт коммит с двумя родителями; PR обновляется после последующего push.
При конфликте Git останавливается для разрешения файлов.
После разрешения конфликтов выполните `git add -- file`.
Затем выполните `git merge --continue`.
Для отмены выполните `git merge --abort`.
По соглашению команды можно использовать альтернативу: `git rebase origin/main`.
Rebase переписывает вашу ветку.
Для конфликтов rebase используйте `rebase --continue` / `--abort`.
Не создавайте вместо этого произвольный новый merge-коммит.
После опубликованного rebase требуется согласованный push с [проверкой lease](../git/remotes.md).
Не перебазируйте общую интеграционную ветку только ради привычной линейности.

## Выбрать способ слияния

**Ситуация:** PR одобрен и проверки прошли; нужно выбрать вид истории целевой ветки.
Сопоставьте требования проекта с результатом каждого метода.

| Метод GitHub | Результат | Когда уместен |
| --- | --- | --- |
| Merge commit | Сохраняет коммиты head и добавляет merge-коммит | Важны исходные коммиты и топология |
| Squash and merge | Итоговое изменение попадает в один новый коммит | PR — одна логическая задача, промежуточные коммиты не нужны |
| Rebase and merge | Переприменяет коммиты в base с новыми SHA | Нужны отдельные коммиты и линейная история |

Доступность методов задаётся настройками репозитория и правилами ветки.
GitHub rebase-and-merge не тождественен последовательности `git rebase main; git merge`:
последняя без ветки у merge использует upstream текущей ветки и не описывает интеграцию в main.
Локальный `git merge --squash feature` только готовит индекс и рабочее дерево.
Затем нужен `git commit`.
Не обходите GitHub-проверки локальным merge и прямым push в защищённую base.

Справочный CLI-фрагмент изменяет состояние GitHub:

```text
gh pr merge 123 --squash
```

До запуска проверьте условия:

- [ ] Выбран нужный PR.
- [ ] Окончательный diff проверен.
- [ ] Слияние разрешено.

При merge queue используйте предусмотренный репозиторием процесс очереди.

## Проверить результат и удалить ненужную ветку

**Ситуация:** PR слит; нужно удалить feature-ветку, не потеряв локальную или неопубликованную работу.
Проверьте состояние PR и фактическую целевую ветку.
Если применимо, проверьте результат деплоя.
Сохраните незакоммиченную работу перед переключением.

**Пример — фрагмент чтения и обновления локальной `main` из `origin/main`:**

```bash
git switch main
git fetch origin
git merge --ff-only origin/main
git log --oneline origin/main..main
git branch --merged main
```

**Результат:** fast-forward обновляет локальную main при отсутствии расхождения.
Если локальная main опережает `origin/main`, merge может завершиться успешно без публикации этих коммитов.
Вывод `log` показывает такую локальную работу; её наличие требует отдельного разбора.
`branch --merged main` показывает ветки, чьи коммиты стали предками локальной main.
Этот список не доказывает интеграцию после squash и не проверяет серверную ветку.

Проверьте [опубликованный результат и сохранность коммитов](../git/remotes.md#удалить-ветку-после-проверки-результата).
Только затем выберите отдельную операцию удаления:

| Область | Фрагмент | Последствие |
| --- | --- | --- |
| Локальная ветка | `git branch -d feature/profile` | Удаляет локальную ссылку; проверяет включение в upstream либо HEAD |
| Серверная ветка | `git push origin --delete feature/profile` | Удаляет общую ссылку; сначала подтвердите опубликованный результат и отсутствие чужой работы |
| Устаревшие ссылки remote | `git fetch --prune origin` | Удаляет только устаревшие remote-tracking ссылки |

После squash `branch -d` может отказать при сохранённом результате PR.
Изучите `git log main..feature/profile`, конечный diff и итог PR.
[Создайте архивную ветку при необходимости](../git/remotes.md#удалить-ветку-после-проверки-результата).
`-D` отключает проверку включения; применяйте его только после проверки сохранности работы.
Состояние upstream `gone` не доказывает, что локальная ветка больше не нужна.

## Разобраться с неправильным списком коммитов

**Ситуация:** в PR есть коммиты, которые не относятся к задаче.
Проверьте base и head.
Проверьте репозитории base и head.
Затем изучите `git log --oneline --graph --all` и merge-base.
После `git fetch origin` выполните фрагмент для текущей feature-ветки:

```bash
git rev-list --left-right --count origin/main...HEAD
```

**Пример результата:** `2 3` означает два коммита только в известной base и три только в head.
Команда показывает текущие ahead/behind локально.
Слева указаны коммиты только base.
Справа указаны коммиты только head.
История переписанной ветки автоматически отражается в PR.
Старые комментарии могут стать outdated.
Если после force push содержимое неожиданно изменилось, сохраните ссылки на нужные коммиты.
До повторной перезаписи выясните причину изменения.
[Reflog](../git/history.md) помогает изучить локальные прежние состояния.
