# Описание, ревью и проверки PR

Уровень: базовый и средний. Предпосылки: ветка с изменениями, понимание задачи и правил проекта.
[К справочнику Pull Requests](README.md).

## Подготовить понятное предложение

Сначала проверь свой diff: нет ли секретов, отладочных правок и несвязанных изменений.
PR должен содержать достаточно контекста для человека, не читавшего переписку.
Один связный результат удобнее ревьюить; фиксированная граница «до 400 строк» не является правилом GitHub.

Шаблон описания, который следует адаптировать к шаблону конкретного репозитория:

```markdown
## Задача и результат
Что происходило раньше, при каком условии и что теперь меняется.

## Изменения
- Существенные изменения и причина выбранного решения.

## Проверка
- Что выполнено и какой получен результат.
- Что не проверялось и почему это существенно.

## Риски и совместимость
Миграции, несовместимость, ограничения; при необходимости план отката.

## Связанные задачи
Closes #123
```

Для UI добавь сопоставимые снимки до/после. Для изменения поведения укажи конкретный вход и результат.
Не отмечай проверки, которые не выполнял; «тесты проходят» без команды и контекста мало помогает ревьюеру.
Conventional Commits для заголовка — [соглашение проекта](../git/workflow.md#сообщения-коммитов).

## Создать и посмотреть через CLI

Справочные фрагменты для авторизованного `gh` в правильном репозитории. **Не выполнялись**:
первые команды отправляют ветку и создают объект на GitHub.

```text
git push -u origin feature/profile
gh pr create --draft --base main --head feature/profile --title "feat: add profile" --body-file pr-body.md
gh pr view 123 --web
gh pr list
```

Файл `pr-body.md` должен содержать фактическое описание. Перед созданием проверь `git remote -v`
и base/head в интерфейсе. `gh pr create` создаёт PR; для просмотра служит `gh pr view`.

## Действия автора и ревьюера

| Автор | Ревьюер |
| --- | --- |
| Объяснить проблему и границы решения | Сверить изменение с целью и ограничениями |
| Проверить собственный diff | Проверить корректность, краевые случаи, безопасность и совместимость |
| Добавить подходящих ревьюеров | Формулировать конкретные замечания к коду и поведению |
| Ответить на замечания, обосновать несогласие | Отличать обязательное исправление от предложения |
| Отправить исправления в ту же ветку | Повторно проверить существенные правки |

Ревью может завершиться Comment, Approve или Request changes. Новые коммиты могут потребовать
нового approval в зависимости от protections. Сроки ответа и число ревьюеров определяются командой,
а не универсальным правилом «24 часа» или «2+».

## Перед слиянием

- Base/head выбраны верно; просмотрен окончательный diff.
- Выполнены требуемые проверки; обязательные CI checks относятся к нужному состоянию ветки.
- Получены необходимые approvals, обработаны блокирующие обсуждения.
- Нет неразрешённых конфликтов, PR не Draft, требования репозитория соблюдены.
- Выбрана согласованная стратегия слияния и понятны последующие действия.

`gh pr checks 123` показывает проверки; `gh pr ready 123` меняет Draft на готовность к ревью.
Наличие зелёного локального теста не заменяет обязательный серверный check.
