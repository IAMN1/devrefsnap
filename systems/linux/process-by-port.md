# Найти процесс по порту в Linux

Откройте страницу, если приложение сообщает «порт занят» или нужно узнать, кто принимает TCP-соединения на заданном порту.
Начните с протокола, номера порта и окружения, в котором работает приложение.

| Ситуация | Приём | Пример |
| --- | --- | --- |
| TCP-порт 8000 занят | Точный фильтр `ss` и сведения о процессе | [Команда и вывод](#найти-tcp-listener) |
| Строка есть, PID не показан | Проверить права и видимость процессов | [Ограничения прав](#если-pid-не-показан) |
| Приложение в другом контейнере | Проверить сетевой namespace и доступ к `/proc` | [Ограничения namespace](#если-процесс-в-другом-namespace) |
| Нужен UDP либо TCP без LISTEN | Изменить протокол или набор состояний | [Другие сокеты](#проверить-udp-и-другие-состояния-tcp) |
| Нужно повторить проверку с нуля | Создать собственный учебный сокет | [Самостоятельный пример](#самостоятельный-учебный-пример) |

Уровень: средний; диагностика namespace — продвинутый.
Предпосылки: терминал Linux, запуск команд и различение локальной системы, контейнера и удалённого сервера.
Команды чтения требуют `ss` из iproute2 и `ps` из procps-ng.
Учебный пример дополнительно требует Python 3.

Рецепт ищет локальный сокет и процесс.
Для диагностики firewall, рабочих служб и внешней доступности нужны отдельные действия.
На macOS команда `ss` не является штатным инструментом; этот рецепт выполняйте внутри Linux.

## Найти TCP listener

**Ситуация:** нужно узнать процесс, который принимает подключения на TCP-порту 8000.
Порт — номер сетевой конечной точки, например `8000`.
TCP и UDP имеют отдельные наборы портов.
TCP передаёт данные через соединение; UDP передаёт отдельные сообщения без установления такого соединения.
Сокет — объект ОС для сетевого обмена; процесс может держать несколько сокетов.
TCP listener — сокет в состоянии `LISTEN`, готовый принимать подключения.
PID — числовой идентификатор процесса в видимом пространстве процессов.

**Команда — фрагмент для вашей Linux-системы:**

```bash
ss -lntp 'sport = :8000'
```

Замените `8000` нужным портом.
`-l` выбирает слушающие сокеты, `-n` оставляет числовые адреса и порты.
`-t` выбирает TCP, `-p` добавляет процессы при доступных сведениях.
Фильтр `sport` задаёт локальный порт сокета; для listener нужен локальный порт, а не порт удалённого клиента.
Кавычки передают фильтр оболочке как один аргумент.
Точный фильтр не путает `8000` с `18000`, как поиск подстроки через `grep 8000`.

**Ожидаемый результат — иллюстрация вывода:**

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:Port Process
LISTEN 0      8      127.0.0.1:8000    0.0.0.0:*        users:(("python3",pid=4312,fd=3))
```

PID, имя процесса, очереди, дескриптор и выравнивание зависят от вашей системы.
`pid=4312` обозначает процесс, а `fd=3` — номер открытого дескриптора сокета внутри процесса.
`127.0.0.1:8000` в колонке `Local Address:Port` означает привязку к loopback текущего сетевого namespace.
Loopback предназначен для обращения к этому сетевому окружению изнутри.
В той же колонке `0.0.0.0:8000` означает все IPv4-интерфейсы этого namespace.
`[::]:8000` обозначает IPv6 wildcard; приём IPv4 дополнительно зависит от настроек сокета и ядра.
Колонка `Peer Address:Port` у listener не указывает подключённого клиента.

Для найденного PID уточните пользователя и команду запуска.
Замените `4312` фактическим PID из вывода `ss`:

```bash
ps -p 4312 -o pid,user,comm,args
```

**Результат:** `ps` показывает PID, пользователя, короткое имя и аргументы процесса.
Для показанного примера имя обычно будет `python3`; аргументы зависят от способа запуска.
Процесс может завершиться между `ss` и `ps`; PID впоследствии может получить другой процесс.
Перед изменением состояния повторно проверьте процесс и его назначение.
Наличие listener не доказывает исправность HTTP или доступность через firewall, NAT и proxy.
Несколько строк или процессов допустимы при разных адресах, IPv4/IPv6, наследовании сокета и `SO_REUSEPORT`.

## Если PID не показан

**Ситуация:** строка `LISTEN` видна, но поля `users:(...)` нет.
Сведения о сокете и сведения о процессе имеют разные ограничения доступа.
Для связи сокета с процессом `ss -p` читает доступные сведения о дескрипторах в `/proc`.
`/proc` — виртуальная файловая система со сведениями о процессах и ядре.
Обычный пользователь обычно видит свои процессы; чужие PID могут не отображаться.

Если у вас есть административные права на этой Linux-системе, повторите чтение:

```bash
sudo ss -lntp 'sport = :8000'
```

`sudo` выполняет команду с разрешёнными административными правами; сама команда `ss` здесь только читает состояние.
Повышение прав может открыть сведения о чужом процессе, но не гарантирует их доступность.
Root — административный пользователь с числовым идентификатором 0.
Capabilities — отдельные разрешения ядра, которые могут ограничиваться независимо от имени пользователя.
Настройки `/proc`, политики безопасности, capabilities и ограничения контейнера могут скрывать сведения и от root.
Root внутри контейнера не получает автоматически права root Linux-хоста.
Повышение прав не переключает сетевой namespace.

Если строк данных нет, проверьте протокол, адрес, состояние сокета и namespace.
С `-H` команда убирает заголовок:

```bash
ss -H -lntp 'sport = :8000'
```

Пустой вывод при успешном завершении означает отсутствие подходящего видимого TCP listener в момент проверки.
Это не доказывает, что порт свободен во всех окружениях и для всех способов привязки.
Ошибку команды и отсутствие совпадений оценивайте отдельно.

## Если процесс в другом namespace

Network namespace — отдельное сетевое окружение Linux со своими интерфейсами, маршрутами и сокетами.
Одинаковый порт может использоваться независимо в разных сетевых namespace.
`ss` по умолчанию смотрит сетевой namespace своей команды.
Контейнеры часто имеют отдельный network namespace, но могут разделять сеть с другим контейнером или хостом.

PID namespace задаёт видимость процессов и их номера.
Для одного процесса PID на хосте и PID внутри контейнера могут различаться.
Видимость сокетов определяется сетью, а возможность сопоставить процесс зависит также от видимых процессов и `/proc`.
В общей сети при разных PID namespace root может видеть listener без имени и PID владельца.

**Выбор контекста:** выполните `ss` внутри окружения приложения через разрешённый механизм входа в контейнер.
Убедитесь, что `ss` установлен в этом окружении.
Опубликованный порт контейнера и внутренний порт приложения могут отличаться.
Переадресация через NAT может работать без отдельного listener приложения на опубликованном порту хоста.

Если известен PID процесса в целевом окружении, сравните ссылки namespace.
Фрагмент предназначен для Linux-системы, где PID `4312` виден через `/proc`:

```bash
readlink /proc/self/ns/net
readlink /proc/4312/ns/net
```

Одинаковые значения вида `net:[4026532001]` означают один network namespace.
Ошибка доступа или исчезнувший процесс не позволяют сделать такое сравнение.

При достаточных правах администратор Linux-хоста может выполнить `ss` в сетевом namespace известного процесса:

```bash
sudo nsenter --target 4312 --net -- ss -lntp 'sport = :8000'
```

`nsenter` запускает новую команду в выбранном namespace.
Замените `4312` PID, видимым в контексте, из которого вызывается `nsenter`.
`--net` меняет только сетевой namespace; PID namespace и `/proc` остаются прежними.
Поэтому получение списка сокетов ещё не гарантирует видимость всех процессов.
Для входа требуются разрешения ядра, включая соответствующие capabilities; `sudo` внутри ограниченного контейнера может быть недостаточно.

## Проверить UDP и другие состояния TCP

Для UDP-порта 8000 используйте отдельный запрос:

```bash
ss -uanp 'sport = :8000'
```

`-u` выбирает UDP, а `-a` включает связанные и несвязанные UDP-сокеты.
У UDP нет TCP-состояния `LISTEN`; ожидайте, например, `UNCONN` или `ESTAB`.
UDP-порт с тем же номером не является тем же TCP-сокетом.

Если нужны TCP listener и установленные соединения на локальном порту 8000, используйте:

```bash
ss -antp 'sport = :8000'
```

Эта команда включает установленные соединения и listener.
Для поиска по удалённому порту используйте `dport` вместо `sport`.

## Самостоятельный учебный пример

Создайте отдельную учебную папку в Linux.
Проверьте наличие инструментов:

```bash
ss -V
ps --version
python3 --version
```

В Debian пакет `iproute2` предоставляет `ss`, `procps` предоставляет `ps`, а `python3` — интерпретатор.
Установку пакетов согласуйте с правилами вашей учебной системы.
Пример не требует `sudo` при обычной доступности сведений о собственном процессе.

Сохраните полный блок как `port_probe.py`.
Запустите `python3 port_probe.py` из папки с этим файлом.
Программа создаёт свой TCP-сокет на `127.0.0.1` и просит ОС выбрать свободный порт.
Программа не принимает запросы, не публикует файлы и закрывает только свой сокет.

<!-- example: linux/port_probe.py -->
```python
import os
import socket
import subprocess


def scan(port):
    return subprocess.run(
        ["ss", "-H", "-lntp", f"sport = :{port}"],
        check=True, capture_output=True, text=True, timeout=5,
    ).stdout


with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as listener:
    listener.bind(("127.0.0.1", 0))
    listener.listen(8)
    port = listener.getsockname()[1]
    pid = os.getpid()
    output = scan(port)
    assert f"127.0.0.1:{port}" in output
    assert f"pid={pid}," in output, "PID не виден: проверьте права и /proc"
    print(f"TCP port={port}; PID={pid}")
    print(output.strip())
    subprocess.run(
        ["ps", "-p", str(pid), "-o", "pid,user,comm,args"],
        check=True, timeout=5,
    )

assert not scan(port).strip(), "Порт уже появился в другом listener"
print("После закрытия: listener не найден")
```

**Ожидаемый результат:** вы видите выбранный порт, PID Python, строку `LISTEN`, результат `ps` и сообщение об отсутствии listener после закрытия.
Запускайте без `python3 -O`, чтобы сохранить проверки `assert`.
В редком случае другой процесс может занять тот же порт между закрытием и повторным чтением.
Пример не проверяет сетевую доставку данных.

- [ ] Сопоставьте PID из `ss` с PID программы и выводом `ps`.
- [ ] Проверьте локальный адрес и протокол.
- [ ] Различайте отсутствие listener и отсутствие сведений о процессе.
- [ ] Для контейнера проверьте сетевой namespace и видимость процессов.
- [ ] Повторите чтение перед любым изменением состояния процесса.
