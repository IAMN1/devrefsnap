# Спроектировать Python-проект

Используйте руководство, чтобы превратить требования в структуру кода, способ проверки и план изменений.
Открывайте руководство при старте проекта или пересмотре границ проекта.
Результат работы — решения и проверяемые артефакты в вашем репозитории.
Руководство не задаёт универсальную конфигурацию приложения.

## Базовый уровень

### Определить задачу до выбора архитектуры

Запишите несколько реальных сценариев.
Для каждого сценария укажите, кто вызывает приложение.
Укажите результат сценария.
Укажите сохраняемые данные.
Укажите, что считается ошибкой.
Добавьте пример входа для каждого сценария.
Добавьте критерий приёмки для каждого сценария.

| Нужно выяснить | Пример конкретного ответа | Где хранить |
| --- | --- | --- |
| Назначение | CLI импортирует каталог; API ищет товары | README и описание сценариев |
| Граница данных | Кто создаёт товар, кто вправе его изменить | Схема данных и правила доступа |
| Ограничения | Есть ли офлайн-работа, персональные данные, требование совместимости | Описание требований |
| Нагрузка | Объём каталога, параллельные запросы, допустимое время ответа | План измерения / результаты теста |
| Эксплуатация | Кто развёртывает, наблюдает и восстанавливает | Инструкция запуска и runbook |

Запишите неизвестное как вопрос или проверяемую гипотезу.
Назначьте ответственного за ответ.
Размер команды и число сущностей полезны как контекст, но сами по себе не определяют архитектуру.

### Получить первый проверяемый результат

```mermaid
flowchart LR
    R["Сценарий и ограничения"] -->|задают контекст| D["Решение и границы"]
    D -->|направляют| P["Один сквозной сценарий"]
    P -->|проверяется| T["Тест и запуск"]
    T -->|дают данные| F["Измерение и обратная связь"]
    F -->|уточняет| D
```

Схема показывает цикл работы.
Схема не задаёт календарный план.
Первый сквозной сценарий проходит от входа до результата.
Пример: загрузка учебного каталога → поиск существующего товара → понятная ошибка для отсутствующего товара.
Рабочий пример приведён [здесь](example.md).

## Средний уровень

### Принять решения и собрать воспроизводимый проект

| Решение | Что должно быть явно определено |
| --- | --- |
| Структура | Границы модулей, публичные интерфейсы, направление импортов |
| Стек | Причина выбора библиотеки, поддерживаемая версия Python, ограничения эксплуатации |
| Упаковка | `pyproject.toml`, build backend, import package, точка запуска |
| Зависимости | Область жизни объектов, место их создания и закрытия |
| Конфигурация | Обязательные параметры, defaults, источник значений, валидация при запуске |
| Тестирование | Какое поведение проверяется изолированно, с реальной инфраструктурой и сквозным тестом |
| Ошибки и логи | Как доменная ошибка превращается в ответ; что помогает диагностике без утечки секретов |

Описание интерфейса не требует отдельного класса для каждой функции.
[SOLID](../../../architecture/solid.md) и [паттерны](../../../architecture/patterns/README.md) помогают оценить конкретную границу.
Эти подходы не заменяют требования.

### Оформить проверяемые чек-листы

Чек-лист содержит условия для проверки перед действием.
Оформляйте пункты в Markdown через `- [ ]`.
Так пункты читаются и отмечаются как задачи.
Чек-лист не является Python/YAML-конфигурацией.
Если у команды нет согласованного календарного плана, чек-лист не задаёт «день 1».

- [ ] Опишите основной сценарий.
- [ ] Добавьте пример ожидаемого результата.
- [ ] Проверьте, что новый участник может запустить проект по README в чистом окружении.
- [ ] Проверьте успешный сценарий тестом.
- [ ] Проверьте тестом как минимум одну существенную ошибку.
- [ ] Определите создание каждого внешнего ресурса.
- [ ] Определите время жизни каждого внешнего ресурса.
- [ ] Определите закрытие каждого внешнего ресурса.

Развёрнутые условия для изменения и релиза — [на странице поставки](delivery-and-evolution.md#проверки-готовности).

## Продвинутый уровень

Начните пересмотр границ с наблюдаемой проблемы.
Примеры: долгий релиз, конфликтующие изменения, потребность в независимом масштабировании или недопустимое время восстановления.
Сначала зафиксируйте симптом.
Укажите ограничения.
Определите способ измерить результат.
Затем выберите изменение.
Определите переходный период.

- [Архитектурное решение](structure-and-decisions.md#записать-решение-adr) сохраняет причины и последствия выбора.
- [План изменения](delivery-and-evolution.md#изменения-схемы-данных-и-архитектуры) определяет совместимость, проверку и откат.
- [Метрики](delivery-and-evolution.md#наблюдение-и-метрики) показывают, решена ли исходная проблема.
- Разделение на микросервисы — один из возможных вариантов. Корректно устроенный монолит может оставаться конечным решением.

## Частые ошибки

| Ошибка | Что сделать |
| --- | --- |
| Выбрать микросервисы по числу разработчиков | Сформулируйте необходимость независимого развёртывания. Укажите цену распределённой системы |
| Принять дерево каталогов за архитектуру | Проверьте направление импортов. Проверьте владение данными |
| Применить универсальные проценты тестов и RPS | Выберите сценарии риска и измерения именно этого приложения |
| Переписать всё ради нового стека | Спланируйте обратимый шаг. Проверьте исходную проблему |
| Скопировать `.env.production` с паролем из примера | Определите источник секретов конкретного окружения. Храните в репозитории только безопасный образец |
