# Спроектировать Python-проект

Практическое руководство: как превратить требования в структуру кода, способ проверки и план изменений.
Оно нужно при старте проекта или пересмотре его границ. Результат — решения и проверяемые артефакты
в вашем репозитории, а не универсальная конфигурация приложения.

## Базовый уровень

### Определить задачу до выбора архитектуры

Запишите несколько реальных сценариев: кто вызывает приложение, какой результат получает,
какие данные сохраняются и что считается ошибкой. Для каждого добавьте пример входа и критерий приёмки.

| Нужно выяснить | Пример конкретного ответа | Где хранить |
| --- | --- | --- |
| Назначение | CLI импортирует каталог; API ищет товары | README и описание сценариев |
| Граница данных | Кто создаёт товар, кто вправе его изменить | Схема данных и правила доступа |
| Ограничения | Есть ли офлайн-работа, персональные данные, требование совместимости | Описание требований |
| Нагрузка | Объём каталога, параллельные запросы, допустимое время ответа | План измерения / результаты теста |
| Эксплуатация | Кто развёртывает, наблюдает и восстанавливает | Инструкция запуска и runbook |

Неизвестное записывают как вопрос или проверяемую гипотезу с ответственным за ответ.
Размер команды и число сущностей полезны как контекст, но сами по себе не определяют архитектуру.

### Получить первый проверяемый результат

```mermaid
flowchart LR
    R["Сценарий и ограничения"] -->|задают контекст| D["Решение и границы"]
    D -->|направляют| P["Один сквозной сценарий"]
    P -->|проверяется| T["Тест и запуск"]
    T -->|дают данные| F["Измерение и обратная связь"]
    F -->|уточняет| D
```

Это цикл работы, а не календарный план. Первый сквозной сценарий проходит от входа до результата:
например, загрузка учебного каталога → поиск существующего товара → понятная ошибка для отсутствующего.
Рабочий пример приведён [здесь](example.md).

## Средний уровень

### Принять решения и собрать воспроизводимый проект

| Решение | Что должно быть явно определено |
| --- | --- |
| Структура | Границы модулей, публичные интерфейсы, направление импортов |
| Стек | Причина выбора библиотеки, поддерживаемая версия Python, ограничения эксплуатации |
| Упаковка | `pyproject.toml`, build backend, import package, точка запуска |
| Зависимости | Область жизни объектов, место их создания и закрытия |
| Конфигурация | Обязательные параметры, defaults, источник значений, валидация при запуске |
| Тестирование | Какое поведение проверяется изолированно, с реальной инфраструктурой и сквозным тестом |
| Ошибки и логи | Как доменная ошибка превращается в ответ; что помогает диагностике без утечки секретов |

Описание интерфейса не требует отдельного класса для каждой функции. [SOLID](../../../architecture/solid.md)
и [паттерны](../../../architecture/patterns/README.md) помогают оценить конкретную границу, но не заменяют требования.

### Оформить проверяемые чек-листы

Чек-лист — список условий, которые проверяют перед действием. В Markdown пункты пишут обычными
`- [ ]`, чтобы они читались и отмечались как задачи. Чек-лист не является Python/YAML-конфигурацией
и не задаёт «день 1», если у команды нет согласованного календарного плана.

- [ ] Описан основной сценарий и пример ожидаемого результата.
- [ ] Новый участник может запустить проект по README в чистом окружении.
- [ ] Тест показывает успешный сценарий и как минимум одну существенную ошибку.
- [ ] Для каждого внешнего ресурса определены создание, время жизни и закрытие.

Развёрнутые условия для изменения и релиза — [на странице поставки](delivery-and-evolution.md#проверки-готовности).

## Продвинутый уровень

Пересмотр границ начинается с наблюдаемой проблемы: долгого релиза, конфликтующих изменений,
независимого масштабирования или недопустимого времени восстановления. Сначала фиксируют симптом,
ограничения и способ измерить результат, затем выбирают изменение и переходный период.

- [Архитектурное решение](structure-and-decisions.md#записать-решение-adr) сохраняет причины и последствия выбора.
- [План изменения](delivery-and-evolution.md#изменения-схемы-данных-и-архитектуры) определяет совместимость, проверку и откат.
- [Метрики](delivery-and-evolution.md#наблюдение-и-метрики) показывают, решена ли исходная проблема.
- Разделение на микросервисы — один из возможных вариантов; корректно устроенный монолит может оставаться конечным решением.

## Частые ошибки

| Ошибка | Что сделать |
| --- | --- |
| Выбрать микросервисы по числу разработчиков | Сформулировать необходимость независимого развёртывания и цену распределённой системы |
| Принять дерево каталогов за архитектуру | Проверить направление импортов и владение данными |
| Применить универсальные проценты тестов и RPS | Выбрать сценарии риска и измерения именно этого приложения |
| Переписать всё ради нового стека | Спланировать обратимый шаг и проверить исходную проблему |
| Скопировать `.env.production` с паролем из примера | Определить источник секретов конкретного окружения; в репозитории хранить только безопасный образец |
