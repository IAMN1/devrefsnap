## INNER JOIN и LEFT JOIN — 12 ноября

В обеих версиях [карточки JOIN](../../docs/ru/databases/sql/queries.md#сравнить-inner-join-и-left-join) совпадают два SQL-запроса.
После загрузки [учебного набора](../../examples/databases/sql/demo.sql) выполнили оба запроса на SQLite 3.53.4 в памяти и на PostgreSQL 18.6 в одноразовом контейнере без сети.
Обе СУБД вернули `alice|1`, `alice|2`, `bob|3` для INNER JOIN.
LEFT JOIN вернул те же строки и добавил `carol|NULL`.
Проверили строки и порядок на [отрисованной схеме](../../docs/assets/sql-joins.svg).
Правила сопоставления и добавления NULL сверили с [документацией PostgreSQL 18](https://www.postgresql.org/docs/18/queries-table-expressions.html#QUERIES-JOIN).

## Проверки иллюстраций — 15 ноября 2026

При аудите повторили INNER JOIN и LEFT JOIN на SQLite 3.53.4 в памяти. Получены три строки INNER JOIN и четвёртая строка `carol` с `NULL` в LEFT JOIN. PostgreSQL в этом проходе JOIN не запускали; прежний прогон обеих СУБД описан выше.

В локальном Redis 7.4.11 с redis-py 8.1.0 выполнили примеры [WATCH](../../examples/databases/non-relational/redis/transactions.py) и [Streams](../../examples/databases/non-relational/redis/messaging.py). Изменение watched-ключа вторым соединением прервало транзакцию. `XACK` снял запись с pending, а дополнительный `XRANGE` подтвердил сохранение тела записи с тем же id.

Запись сохраняет отдельный прогон этих сценариев на Redis 7.4.11. Прежние результаты Redis 8.2 приведены в разделе [Redis](#redis--6-ноября). Проверок persistence, failover или аварийной повторной доставки 15 ноября не было. [Условия просмотра GIF](navigation-review.md#публичный-вход-и-gif--15-ноября-2026).

### Исправление TTL-карточки — 8 ноября

Независимое ревью выявило P2: `SET KEEPTTL` создавал бессрочный ключ, если прежний ключ исчез.
[Карточка](../../docs/ru/databases/non-relational/redis/data-and-caching.md#обновить-значение-и-сохранить-срок) исправлена на `xx=True, keepttl=True` с обработкой `None`.
`XX` не проверяет наличие TTL; конкурентный `PERSIST` требует отдельного атомарного протокола.
Полный `data.py` не менялся.

Среда адресной проверки: macOS arm64, Python 3.14.6, Redis 8.2.11, redis-py 8.1.0.
Redis собран во временной папке с `MALLOC=libc BUILD_TLS=no`; системная служба не устанавливалась.
Точный блок карточки извлечён из Markdown и выполнен через собственный Redis без TCP/persistence.
Обёртка клиента удаляла собственный ключ непосредственно перед вторым SET.

| Проверка | Фактический результат |
| --- | --- |
| Прежняя карточка и удаление между командами | `AssertionError` на TTL; дефект воспроизведён |
| Исправленная карточка, volatile-ключ существует | `True`, новое значение Ada Lovelace; PEXPIRETIME прежний, PTTL положителен |
| Исправленная карточка, ключ удалён | `None`, новый ключ не создан, TTL=-2; сообщение об отсутствии ключа |
| Очистка | Собственный Redis остановлен; временный каталог с сокетом удалён |

Команда проверки: `/tmp/redis-ttl-card-check/venv/bin/python /tmp/redis-ttl-card-check/check_card.py`, код 0.
Рецензент принял исправление узкой повторной проверкой; полного Redis-набора не повторял.
Реальное истечение таймера, eviction, конкурентный PERSIST и восстановление после сбоя отдельно не воспроизводились.

10 ноября серверные программы не запускались: проверены сохранность блоков, якоря и синтаксис.
Redis latest сопоставлялся с выбранной веткой 8.2; новые API других веток не переносились.
Исторические прогоны не доказывают совместимость всех версий или пригодность к рабочим объёмам.
