## Существенное техническое замечание

### P2 — KEEPTTL может превратить исчезнувший кеш в бессрочный ключ

**Файл:** `databases/non-relational/redis/data-and-caching.md`, строки 32–43 в версии до исправления; непосредственно обновление — строка 37.

**Сценарий читателя:** кеш должен исчезнуть через 60 секунд; позднее приложение обновляет значение с сохранением исходного срока.
Карточка показывает `client.set(cache, value, keepttl=True)` и обещает продолжение исходного срока.
Между первоначальной записью и обновлением ключ может истечь либо исчезнуть из-за eviction или удаления.
Строка 43 уже допускает исчезновение ключа, но не объясняет последствие последующего SET.

**Подтверждённое поведение:** обычный SET создаёт отсутствующий ключ.
KEEPTTL сохраняет существующий срок, но не задаёт срок заново для отсутствующего ключа.
Следовательно, после исчезновения обновление создаёт ключ без срока; TTL возвращает `-1`.
Проверка `assert` обнаружит нарушение после записи, но не отменит создание бессрочного ключа.

**Минимальная последовательность для воспроизведения в отдельном учебном Redis:**

```text
SET cache Ada EX 60
DEL cache
SET cache "Ada Lovelace" KEEPTTL
TTL cache
# -1
```

`DEL` здесь детерминированно моделирует исчезновение между командами; рецензент не выполнял эти команды на пользовательском Redis.

**Основание:** официальные [SET](https://redis.io/docs/latest/commands/set/) и [TTL](https://redis.io/docs/latest/commands/ttl/).
Сверено описание создания ключа, KEEPTTL, XX и значения TTL=-1.
Дополнительный runtime-запуск рецензента не выполнен: прежний временный бинарный Redis из отчёта уже недоступен.

**Конкретное исправление:** для изменения только существующего ключа показать `xx=True, keepttl=True` и обработать `None` при исчезнувшем ключе.
Отдельно указать, что рецепт предполагает существующий срок и отсутствие конкурентного PERSIST/изменения TTL.
Если исчезнувший ключ нужно создать заново, явно выбрать новую политику срока, а не молча полагаться на KEEPTTL.
Согласовать карточку с полной программой или явно обозначить более сильную границу карточки.

**Состояние:** координатор принял P2 и передал исходному исполнителю databases.
На момент записи отчёта исправление ещё требует узкой повторной проверки.
