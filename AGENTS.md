# Правила работы с репозиторием

Репозиторий содержит шпаргалки и практические материалы по разработке на русском и английском языках.
Цель — быстро найти правильный пример и перейти к подробному объяснению.
Выберите язык в [корневом каталоге](README.md).
Для поиска действия используйте указатель задач на [русском](docs/ru/tasks/README.md) или [английском](docs/en/tasks/README.md).

## Стиль русского текста: STE 80%

Используйте русский профиль «STE 80%» в русскоязычных материалах.
Название обозначает выбранный редакторский стиль, а не измеренное соответствие английскому стандарту ASD-STE100.
Образец профиля — [версия «80%»](templates/ste-comparison/ste-80.md).

- Пишите одно указание в одном предложении.
- В объяснении раскрывайте одну основную мысль за предложение.
- Ориентируйтесь на 20 слов в инструкции.
- Ориентируйтесь на 25 слов в объяснении.
- Сохраняйте полную грамматическую конструкцию при сокращении текста.
- Обращайтесь к читателю на «вы».
- Начинайте инструкцию с действия: «Создайте», «Запустите», «Проверьте».
- Ставьте условие перед действием, если условие определяет порядок выполнения.
- Используйте активный залог, когда исполнитель известен.
- Называйте объект повторно, если местоимение допускает разные толкования.
- Используйте один термин для одного понятия.
- Сохраняйте точные имена API, команд, параметров и общепринятых терминов.
- Группируйте связанные пояснения в короткие абзацы.
- В таблицах сохраняйте короткие однозначные формулировки.
- Различайте действие, ожидаемый результат и ограничение.
- Сохраняйте условия и степень уверенности исходного утверждения: «может», «обычно», «если».
- Сохраняйте технический смысл при упрощении предложения.

Код, команды, конфигурации, вывод и диаграммы проверяйте отдельно от редакторской правки.
Сохраняйте цитаты и зафиксированные сравнительные образцы в исходном стиле.
Файлы `current.md`, `ste-75.md` и `ste-80.md` в `templates/ste-comparison/` остаются архивом эксперимента.

## Коммиты и Pull Requests

Пишите заголовки и тела коммитов на английском языке.
Используйте Conventional Commits: `<type>[(scope)]: <action and result>`.
Выбирайте тип по изменению: `docs`, `ci`, `fix`, `test`, `refactor`, `chore` или `feat`.
Начинайте описание с действия в повелительной форме.
Ориентируйтесь на 72 символа в заголовке и опускайте точку в конце.
Добавляйте тело, если нужно объяснить причину или существенные ограничения.

Готовьте заголовок и описание PR от имени сопровождающего на английском языке.
Участники могут писать заголовки и описания issues и PR на русском или английском языке. [Правила участия](CONTRIBUTING.md#русский).
Описывайте изменения и их последствия для читателя или системы.
Начинайте с краткого описания; добавляйте технические подробности для существенных изменений.
Указывайте ограничения, если они связаны с изменением и влияют на решение о слиянии.
Добавляйте результаты проверок, если они помогают оценить изменение.
Задавайте merge-коммиту осмысленный английский заголовок с номером PR.

Перед переводом репозитория в публичный режим напомните пользователю о [защите main](maintenance/plans/public-release.md).

## Размещение

- Храните читательские страницы в `docs/ru/` и `docs/en/`.
  Используйте одинаковые пути внутри языковых каталогов для страниц одной темы.
  Добавляйте ссылку на другую языковую версию страницы.
- Храните общие полные файлы примеров в `examples/`.
  Ссылайтесь на один исполняемый файл из обеих версий.
- Применяйте следующие правила путей внутри каждого языкового каталога.
- Размещайте Python и инструменты его экосистемы в `python/`.
- Размещайте Go и его инструменты в `go/`.
- Размещайте материалы об операционных системах в `systems/`.
- Размещайте общие архитектурные принципы, SOLID и паттерны в `architecture/`.
- Размещайте применение архитектуры к Python-проекту в `python/architecture/`.
- Размещайте SQL и СУБД в `databases/`.
- Размещайте библиотеки доступа к БД для Python в `python/databases/`.
- Размещайте общие инструменты разработки в `tools/`.
- Выбирайте одно основное место для каждой темы.
- Связывайте смежные материалы относительными ссылками.
- Используйте английские имена в нижнем регистре.
- Разделяйте слова в именах дефисами.
- Называйте файлы навигации `README.md`.
- Поддерживайте `README.md` в каждом верхнеуровневом каталоге.
  Укажите назначение раздела.
  Укажите границы раздела.
  Добавьте ссылки на содержимое.
- При добавлении или переносе темы обновите каталог соответствующей языковой версии.
  Обновите README её раздела.
  Обновите указатель задач и входящие ссылки.
  При переносе сохраните прежние адреса и якоря через ссылки на новые разделы.

## Формат материала

Перед созданием или переработкой страницы выберите [шаблон по её роли](templates/README.md#выбор-формата).
Храните краткий материал в одном `.md`-файле.
Для объёмной темы создайте каталог.

| Файл | Назначение |
| --- | --- |
| `README.md` | Назначение и быстрый выбор задач темы |
| Страница с предметным именем | Самостоятельная задача, например `testing.md` или `backup-and-restore.md` |
| `recipes.md` | Несколько небольших рецептов, которые удобно читать вместе |

Разделите материал по самостоятельным задачам, если подробные примеры мешают быстрому поиску.
Разделите страницы, если задачи имеют разные зависимости или используются независимо.
По мере роста разделяйте и `recipes.md`.
Количество строк помогает заметить проблему организации.
Количество строк не задаёт обязательную границу.

Организуйте справочник по задачам читателя.
Используйте уровни, если они помогают выбрать задачу; отдельный раздел для каждого уровня необязателен.
Сохраняйте полезное содержание прежних уровней при изменении структуры.
Для полного примера укажите собственные предпосылки и зависимости.

| Роль | Содержание | Шаблон |
| --- | --- | --- |
| Шпаргалка | Задача, короткий пример, результат и существенное условие | [Краткий справочник](templates/cheat-sheet.md) |
| Самостоятельный пример | Минимальная подготовка, полный код, запуск и ожидаемый результат | [Полный пример](templates/standalone-example.md) |
| Процедура | Предпосылки, порядок действий, проверка результата и восстановление при отказе | [Процедура](templates/procedure.md) |

Каталоги содержат назначение раздела и прямые входы в материалы.
Служебные документы сохраняют свой формат.

### Быстрое повторение

- На первом экране укажите назначение материала.
  Укажите условие применения.
  Если задач несколько, добавьте компактный выбор «задача → приём → пример».
- Размещайте условия применения и зависимости после обзора.
  Размещайте длинное оглавление после обзора.
- Покажите в карточке ситуацию, приём, короткий пример, результат и существенное условие.
  Объединяйте связанные пояснения; отдельная подпись для каждого элемента необязательна.
- Связывайте полный код с карточкой прямой ссылкой.
  Так же связывайте длинное объяснение.
- Сравнивайте варианты таблицей решений.
- Используйте чек-лист для самостоятельных действий читателя в процедуре.
  Если таблица уже содержит ожидаемые результаты, оставьте один перечень результатов.
  Если тесты уже проверяют названные случаи, объясните их результат без повторного ручного списка.
- Перед деревом или схемой укажите смысл представления.
  Различайте исходники, зависимости кода, вызовы, этапы изменения и развёртывание.
- Подписывайте отношения на стрелках.
- Показывайте дерево пакетов как возможную реализацию.
  Подписывайте роли файлов.
  Сам паттерн не задаёт обязательное дерево каталогов.

## Содержание и примеры

- Пишите объяснения на языке версии материала. Для английских страниц в `docs/en/` используйте английский язык.
- Стройте раздел вокруг задачи: действие → пример → ожидаемый результат → существенные ограничения.
- На базовом уровне покажите первые рабочие операции.
- На среднем уровне покажите типовые сочетания возможностей.
- На продвинутом уровне разберите сложные случаи, конкурентность, оптимизацию или эксплуатацию.
- Обозначайте блок как полный пример, продолжение конкретного примера, фрагмент или псевдокод.
- Для полного примера укажите зависимости.
  Укажите импорты.
  Укажите подготовку данных.
  Укажите способ запуска.
- Подготовка относится к конкретному примеру.
  Для независимых задач показывайте отдельные минимальные установки и прямые ссылки.
- Храните развёрнутое объяснение в одном основном месте.
  На связанных страницах оставляйте нужный контекст и прямую ссылку.
- Согласуйте имена моделей, поля таблиц, URL и результаты внутри одного примера.
- Для SQL отделяйте команды оболочки от команд `psql`.
  Отделяйте SQL от обоих видов команд.
  Укажите диалект и особенности версии.
- Поясняйте последствия удаления, изменения истории, миграции и восстановления рядом с командой.
  Проверяйте такие рецепты на отдельном учебном окружении с синтетическими данными.
- Сохраняйте полезное покрытие исходного материала.
  Подробности можно переносить на связанные страницы.
- Если рецепт пока не готов, явно укажите его границы.
  Добавьте официальный источник.
- Для численного сравнения укажите условия измерения.
  Добавьте источник чисел.
- Укажите условия применения рекомендации.
- Добавляйте полезные Mermaid-схемы для потоков, состояний, зависимостей и взаимодействия компонентов.
- Для графика с числовыми осями укажите данные или измерения.

## Актуальность

- Проверяйте изменяемые сведения по официальной документации нужной ветки.
  Проверяйте release notes этой ветки.
- Для СУБД предпочитайте ссылки с номером major-версии.
- Различайте сверку с документацией и выполнение примера.
- Сохраняйте значимые результаты проверок по правилам служебных материалов ниже.
- Указывайте диапазон совместимости только при наличии основания.
- В учебном материале указывайте версии API и зависимости, необходимые для запуска примера.
- Показывайте устаревший API в разделе миграции.
  Укажите версию изменения API.

## Читательские и служебные материалы

Шпаргалки содержат задачи, объяснения, примеры, зависимости, ожидаемый результат, существенные ограничения и источники.
Указывайте условия применения прямо рядом с командой или примером.
Сохраняйте учебные тесты и инструкции проверки результата.

Для обычной редакторской правки достаточно осмысленного коммита, PR при публикации и CI.
Отдельный отчёт для каждой такой правки не нужен.

Храните причины существенных решений и полезные результаты проверок в `maintenance/reports/`.
Для сложного или рискованного примера сохраните краткую запись проверки.
Это относится, например, к восстановлению БД, миграции или настройке безопасности.
Укажите дату, версии, команды или сценарий, фактический результат и существенные непроверенные границы.
Дополняйте существующую тематическую запись, если отдельный документ не помогает найти результат.
Сохраняйте исходные даты при переносе исторических проверок.

Ведите [очередь работ](maintenance/plans/README.md) для всех открытых этапов.
Записывайте согласованные и отложенные этапы, когда меняется план.
Различайте порученные задачи и предложения.
Перед выбором следующей задачи сверяйте очередь с исходным поручением и договорённостями из связанных чатов.
При передаче работы укажите открытую очередь и следующий согласованный шаг.
Перед сокращением плана перенесите в очередь все незавершённые пункты.
После завершения плана извлеките полезные решения и доказательства.
Затем сократите или удалите завершённый план и дублирующие отчёты обычным новым коммитом.
Предыдущие версии остаются в Git; уборка документации не требует переписывания истории.
Используйте Git и PR для истории изменений, ревью и операций с ветками.
Подробные журналы действий агента и промежуточные счётчики не требуют постоянного хранения.

Не размещайте служебные паспорта, статусы редактуры и отчёты о работе агента в читательских страницах.
Если служебная запись содержит важное ограничение, сохраните это ограничение рядом с применимым примером.
Указывайте на странице требования запуска и существенные версионные границы.

## Проверка перед завершением

- [ ] Проверьте относительные ссылки.
- [ ] Проверьте якоря оглавлений.
- [ ] Проверьте языки ограждений кода.
- [ ] Проверьте парность ограждений кода.
- [ ] Проверьте Python-примеры компиляцией.
- [ ] По возможности выполните полные примеры с указанными зависимостями.
- [ ] Для SQL используйте соответствующую СУБД или явно укажите сверку только с документацией.
- [ ] Для тестового примера проверьте значимое поведение: успех, ошибку валидации или отказ доступа.
- [ ] Проверьте достижимость перенесённых разделов из оглавления темы.
- [ ] Проверьте отсутствие противоречащих копий.
- [ ] Перечислите изменения, выполненные проверки и существенные непроверенные сценарии в итоговом сообщении.
- [ ] Сохраните значимые доказательства по правилам служебных материалов выше.

Выбирайте проверки примеров по изменению.
Для разовой проверки размещайте зависимости в отдельном временном окружении.
Добавляйте постоянную инфраструктуру, когда она нужна самому материалу.
