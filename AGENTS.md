# Правила работы с репозиторием

Репозиторий содержит русскоязычные шпаргалки и практические материалы по разработке.
Цель — быстро найти правильный пример и при необходимости перейти к подробному объяснению.
Начинай знакомство с [каталога материалов](README.md).

## Размещение

- Python и инструменты, привязанные к его экосистеме, размещай в `python/`.
- Go и его инструменты размещай в `go/`, операционные системы — в `systems/`.
- Общие архитектурные принципы, SOLID и паттерны размещай в `architecture/`;
  применение к конкретному Python-проекту — в `python/architecture/`.
- SQL и СУБД размещай в `databases/`; библиотеки доступа к БД для Python — в `python/databases/`.
- Общие инструменты разработки размещай в `tools/`.
- У каждой темы одно основное место. Смежные материалы связывай относительными ссылками.
- Используй английские имена в нижнем регистре, слова разделяй дефисами. Файлы навигации называй `README.md`.
- В каждом верхнеуровневом каталоге поддерживай `README.md`: назначение, границы раздела и ссылки на содержимое.
- При добавлении или переносе темы обновляй корневой каталог, README соответствующего раздела и входящие ссылки.

## Формат материала

Перед созданием или переработкой темы прочитай [общий шаблон](templates/cheat-sheet.md).
Краткий материал хранится в одном `.md`-файле. Объёмная тема получает собственный каталог:

- `README.md` — назначение, совместимость, быстрый поиск, базовый, средний и продвинутый уровни;
- самостоятельные страницы с предметными именами, например `testing.md` или `backup-and-restore.md`;
- `recipes.md` — несколько небольших рецептов, пока они удобно помещаются на одной странице.

Разделяй материал по самостоятельным задачам, когда подробные примеры мешают быстрому поиску,
у разделов различаются зависимости или ими пользуются независимо. Количество строк — повод
пересмотреть организацию, а не обязательная граница. По мере роста разделяй и `recipes.md`.
Сохраняй три уровня в кратком справочнике; на подробной странице указывай её уровень и предпосылки.
Не создавай пустые уровни и страницы ради симметрии.

### Быстрое повторение

- На первом экране дай назначение, условие применения и компактный выбор «задача → приём → пример».
  Паспорт проверки и длинное оглавление размещай после этого обзора.
- Карточку строй как «проблема → изменение → короткий пример → результат / ограничение».
  Полный код и длинное объяснение связывай прямой ссылкой с карточкой.
- Сравнивай варианты таблицей решений; для проверки действий используй Markdown-чек-листы `- [ ]`.
- Перед деревом или схемой называй её смысл: размещение исходников, зависимости кода,
  вызовы во время выполнения, этапы изменения или развёртывание. Подписывай отношения на стрелках.
- Дерево пакетов показывай как возможную реализацию с ролями файлов, а не обязательную структуру паттерна.

## Содержание и примеры

- Пиши объяснения по-русски; сохраняй точные имена API, команд и общепринятых терминов.
- Строй раздел вокруг задачи: что сделать → пример → ожидаемый результат → существенные ограничения.
- Базовый уровень даёт первые рабочие операции, средний — типовые сочетания возможностей,
  продвинутый — сложные случаи, конкурентность, оптимизацию и эксплуатацию.
- Обозначай блок как полный пример, продолжение конкретного примера, фрагмент или псевдокод.
  Для полного примера указывай зависимости, импорты, подготовку данных и способ запуска.
- Держи имена моделей, поля таблиц, URL и результаты согласованными в пределах одного примера.
- Для SQL отделяй команды оболочки, команды `psql` и сам SQL. Отмечай диалект и особенности версии.
- Для команд удаления, изменения истории, миграций и восстановления поясняй последствия рядом с командой.
  Проверяй такие рецепты на отдельном учебном окружении с синтетическими данными.
- Сохраняй полезное покрытие исходного материала: подробности можно перенести на связанные страницы.
  Если рецепт пока не готов, явно обозначь его границы и дай официальный источник.
- Подкрепляй численные сравнения условиями измерения и источником; рекомендации формулируй с условиями применения.
- Для потоков, состояний, зависимостей и взаимодействия компонентов добавляй полезные Mermaid-схемы.
  Подписывай смысл стрелок; графики с числовыми осями основывай на указанных данных/измерениях.

## Актуальность

- Проверяй изменяемые сведения по официальной документации и release notes нужной ветки.
  Для СУБД предпочитай ссылки с номером major-версии.
- Различай «сверено с документацией» и «выполнено в окружении». Дату и версии записывай отдельно для этих проверок.
- Обозначай диапазон совместимости только при наличии основания; точные версии успешного запуска перечисляй явно.
- Устаревшие API показывай в разделе миграции с указанием версии.
- Статус «актуализировано» относится только к проверенной теме. Перенос файла сам по себе не меняет его статус.

## Проверка перед завершением

1. Проверь относительные ссылки, якоря оглавлений, языки и парность ограждений кода.
2. Проверь Python-примеры компиляцией; полные примеры по возможности выполни с указанными зависимостями.
   Для SQL используй соответствующую СУБД или явно укажи, что выполнена только сверка с документацией.
3. Для тестовых примеров проверь значимое поведение: успешный результат, ошибку валидации или отказ доступа.
4. Проверь, что все перенесённые разделы достижимы из оглавления темы и нет противоречащих копий.
5. В результате работы перечисли изменения, выполненные проверки и существенные непроверенные сценарии.

Репозиторий документационный: проверки примеров выбирай по изменению. Зависимости для разовой проверки
размещай в отдельном временном окружении; постоянную инфраструктуру добавляй, когда она нужна самому материалу.
