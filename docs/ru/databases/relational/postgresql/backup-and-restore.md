
# Создать копию PostgreSQL и проверить восстановление

[English](../../../../en/databases/relational/postgresql/backup-and-restore.md)

Выберите формат копии, восстановите копию в новую БД и проверьте результат.
Рецепты ниже предназначены для отдельного учебного PostgreSQL 18.
[К справочнику PostgreSQL](README.md).

| Ситуация | Выбор | Карточка / пример |

## Выбрать формат и проверить версии

**Ситуация:** нужно выбрать совместимые утилиты и способ восстановления.
Сначала сравните версию сервера и версии клиентов.
Команды оболочки ниже относятся к вашему отдельному учебному серверу:

```bash
pg_dump --version
pg_restore --version
psql --host=127.0.0.1 --username=postgres --dbname=cheatsheet_demo \
  --no-psqlrc --set=ON_ERROR_STOP=1 --command="SHOW server_version;"
```

| Цель | Формат / команда | Восстановление / ограничение |
| --- | --- | --- |
| Архив с выбором объектов | `pg_dump --format=custom` | `pg_restore`; нет параллельного dump |
| Читаемый SQL | `pg_dump --format=plain` | `psql`, а не `pg_restore` |
| Параллельный dump | `pg_dump --format=directory --jobs=4` | Каталог; число процессов выбирают по ресурсам |
| Восстановление к заданному времени | Физическая базовая копия + WAL | Логический dump не заменяет PITR |

**Результат:** формат определяет инструмент восстановления.
Для учебного сценария используйте сервер и клиенты PostgreSQL 18.6.
`pg_dump` не читает сервер более нового major, чем major самого `pg_dump`.
Восстановление в более старый major не гарантируется.


## Создать логическую копию

**Ситуация:** нужна согласованная логическая копия учебной `cheatsheet_demo`.
Исходные данные подготовлены по [queries.sql](query-lab.md#полный-пример-учебная-база).
Роль `postgres` ниже относится только к отдельному учебному серверу.
Пароль вводится по запросу или берётся из настроенного password file.
Для рабочего окружения выберите права и регламент отдельно.

**Пример — фрагмент оболочки:** выполняйте связанные карточки в одной оболочке.

```bash
umask 077
backup_dir=$(mktemp -d)
pg_dump --host=127.0.0.1 --username=postgres --dbname=cheatsheet_demo \
  --format=custom --file="$backup_dir/cheatsheet_demo.dump"
```

**Результат:** при успешном завершении создан архив одной БД.
`pg_dump` получает согласованный снимок при обычной конкурентной работе.
Состав и блокировки сложных операций требуют отдельного планирования.
Не используйте неполный файл после ошибки `pg_dump`.
Архив содержит данные; храните архив с подходящими правами доступа.
Роли и tablespaces кластера в архив одной БД не входят.

[Полный сценарий](backup-lab.md#проверить-custom-plain-и-отказ-восстановления)


## Посмотреть состав архива

**Ситуация:** нужно проверить формат и список объектов перед restore.
Фрагмент продолжает [создание копии](#создать-логическую-копию):

```bash
pg_restore --list "$backup_dir/cheatsheet_demo.dump"
```

**Результат:** список содержит схему `demo`, таблицы, данные и ограничения.
Просмотрите предупреждения `pg_dump` и ожидаемый состав объектов.
Успешный `--list` не доказывает исправность всех данных и возможность полного восстановления.
Восстанавливайте только доверенные архивы.
Restore может выполнить SQL и код, выбранный владельцами исходного сервера.

[Следующий шаг — новая БД](#логическая-копия-и-восстановление-в-новую-бд)


## Логическая копия и восстановление в новую БД

**Ситуация:** нужно проверить архив без изменения исходной БД.
Архив создан по карточке выше; целевой `cheatsheet_restore_check` ещё нет.

**Последствия параметров:** `--no-owner --no-privileges` пропускают исходных владельцев и ACL.
Восстановленные объекты принадлежат роли восстановления.
Для переноса прав рабочей БД составьте отдельный план владельцев и ACL.
`--single-transaction` откатывает изменения restore при ошибке и несовместим с `--jobs`.
Для большой БД единая транзакция может быть неудобна.

**Пример — продолжение в той же оболочке:**

```bash
createdb --host=127.0.0.1 --username=postgres --template=template0 cheatsheet_restore_check && \
pg_restore --host=127.0.0.1 --username=postgres --dbname=cheatsheet_restore_check \
  --single-transaction --exit-on-error --no-owner --no-privileges \
  "$backup_dir/cheatsheet_demo.dump"
```

**Результат:** новая БД содержит восстановленные объекты и данные.
Связка `&&` не запускает restore, если имя целевой БД занято.
Если restore отказал, созданная БД остаётся; изучите ошибку до повторного запуска.
Не добавляйте `--clean` для устранения ошибки: этот параметр удаляет существующие целевые объекты.
Код завершения `0` ещё не подтверждает пригодность восстановленной БД для приложения.

[Проверки результата](#проверить-восстановленную-бд) · [Полный сценарий и ожидаемый отказ](backup-lab.md#проверить-custom-plain-и-отказ-восстановления)


## Восстановить SQL-файл

**Ситуация:** нужна копия в виде SQL, а не custom-архива.
Это самостоятельная альтернатива предыдущим карточкам.
Целевая `cheatsheet_plain_check` должна отсутствовать.

**Пример — фрагмент оболочки для той же учебной исходной БД:**

```bash
umask 077
plain_dir=$(mktemp -d)
pg_dump --host=127.0.0.1 --username=postgres --dbname=cheatsheet_demo \
  --format=plain --no-owner --no-privileges --file="$plain_dir/backup.sql" && \
createdb --host=127.0.0.1 --username=postgres --template=template0 cheatsheet_plain_check && \
psql --host=127.0.0.1 --username=postgres --dbname=cheatsheet_plain_check \
  --no-psqlrc --set=ON_ERROR_STOP=1 --single-transaction --file="$plain_dir/backup.sql"
```

**Результат:** доверенный SQL-файл выполнен в новой БД.
Для plain параметры пропуска владельцев и ACL задаются при dump.
`ON_ERROR_STOP` останавливает выполнение SQL при ошибке.
`--single-transaction` подходит этому полному dump без `--create`.
Для произвольного SQL-файла сначала проверьте совместимость команд с единой транзакцией.
Без единой транзакции ошибка может оставить уже выполненные изменения.

[Полный сценарий custom и plain](backup-lab.md#проверить-custom-plain-и-отказ-восстановления)


## Проверить восстановленную БД

**Ситуация:** restore завершился; нужно проверить данные, схему и поведение.
Фрагмент SQL выполняется в `psql`, подключённом к `cheatsheet_restore_check`:

```sql
SELECT
    (SELECT count(*) FROM demo.users) AS users,
    (SELECT count(*) FROM demo.products) AS products,
    (SELECT count(*) FROM demo.orders) AS orders,
    (SELECT stock FROM demo.products WHERE id = 1) AS keyboard_stock;
```

**Результат для неизменённых учебных данных:** `3 | 3 | 3 | 10`.
Одного подсчёта строк недостаточно.
Равенство данных не доказывает правильность владельцев и прав.

- [ ] Сравните нужные данные с ожидаемым снимком копии.
- [ ] Проверьте состав схемы и необходимых расширений.
- [ ] Проверьте внешние ключи и ограничения.
- [ ] Проверьте генерацию следующего идентификатора.
- [ ] Проверьте запросы и инварианты приложения.
- [ ] Проверьте роли и права по регламенту рабочего окружения.

[Полный SQL проверки](backup-lab.md#проверить-данные-и-ограничения) останавливает учебный сценарий при неверном результате.
Учебные проверки вставок выполняются с rollback, но последовательности identity могут продвинуться даже после rollback.
Запускайте эти проверки только в отдельной восстановленной БД.


## Другие форматы и границы копии

| Задача | Параметры / инструмент | Ограничение |
| --- | --- | --- |
| Параллельный restore | `pg_restore --jobs=4` | Custom/directory; не совмещается с `--single-transaction`; нужен план обработки частичных ошибок |
| Только схема / данные | `--schema-only` / `--data-only` | Для data-only нужна совместимая схема |
| Отдельные таблицы | `--table=demo.orders` | Зависимости могут не попасть в копию автоматически |
| Роли и tablespaces кластера | `pg_dumpall --globals-only` | Отдельный административный экспорт; файл может содержать хеши паролей |

Полная копия рабочей системы может требовать конфигурации, расширений и внешних файлов.
Уточните полноту копии по устройству системы.
Храните копию независимо от исходного хранилища.
Проверяйте восстановление регулярно, а не только чтение архива.


## Удалить только проверочную БД

**Ситуация:** проверка завершена, архив сохранён в нужном месте.
Закройте соединения с проверочной БД.
Команда оболочки **удалит всю БД `cheatsheet_restore_check`**:

```bash
dropdb --host=127.0.0.1 --username=postgres cheatsheet_restore_check
```

Проверьте адрес сервера и точное имя перед запуском.
Исходная `cheatsheet_demo` не является целью этой команды.
Другие учебные БД удаляются отдельно по их именам.


## PITR и репликация

**Продвинутый уровень. Концептуальный маршрут, не готовый сценарий для production.**
PITR восстанавливает кластер из физической базовой копии и непрерывной последовательности WAL.
pg_dump не является базовой копией для PITR.
До настройки определите допустимые потери данных.
Определите допустимое время восстановления.
Задайте правила хранения и доступа.
Запланируйте регулярный тест на отдельном сервере.

1. Настройте доставку WAL в независимое хранилище.
   Проверьте сохранение WAL при повторе доставки.
   Проверьте правильность кодов завершения.
   Настройте контроль пропусков, места и сроков хранения.
2. Получите физическую базовую копию, например pg_basebackup, с нужными правами и WAL.
   Сохраните конфигурацию, версии, tablespaces и ключи доступа отдельно по регламенту.
3. Для тренировки остановите **отдельный целевой** экземпляр.
   Восстановите совместимую базовую копию в data directory целевого экземпляра.
   Обеспечьте доступ к цепочке WAL с начала копии до цели.
4. Задайте restore_command.
   Выберите одну цель восстановления, например recovery_target_time с явной зоной.
   Настройте действие при достижении цели.
   Задавайте параметры в обычной конфигурации PostgreSQL 18.
5. Создайте `recovery.signal` в целевом data directory.
   Запустите целевой экземпляр по документации.
   Проверьте логи.
   Проверьте достигнутую точку восстановления.
   Проверьте данные.
   Примите решение о завершении recovery/promotion отдельно.

`recovery.conf` удалён из PostgreSQL начиная с 12.
Наличие такого файла препятствует запуску.
Для standby используется `standby.signal`.
Не считайте standby.signal и recovery.signal взаимозаменяемыми настройками.
Физическая репликация также опирается на base backup/WAL.
Реплика сама по себе не заменяет резервную копию.
Ошибочное удаление может попасть и на реплику.
Если потребитель отстал, слот репликации может удерживать WAL и заполнить диск.
Настройте наблюдение и ограничения хранения.

Здесь не приведён универсальный `archive_command = 'cp ...'`.
Проверяйте надёжность копирования, повторы, конфликт имён, права, удалённое хранилище и восстановление в конкретном окружении.
Практическую настройку выполняют по [процедуре PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)
и [pg_basebackup](https://www.postgresql.org/docs/18/app-pgbasebackup.html).
