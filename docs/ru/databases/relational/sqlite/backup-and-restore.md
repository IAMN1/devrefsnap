## Выбрать вид копии

| Требование | Приём | Результат / ограничение |
| --- | --- | --- |
| Согласованная копия одной БД | Backup API или `.backup` | Файл SQLite; существующая цель может быть заменена |
| Читаемый SQL | `.dump` | Исполняемый SQL; не является побайтовой копией файла |
| Минимальный размер копии | `VACUUM INTO` | Компактный файл; учитывайте ограничения `VACUUM INTO` |
| Все данные приложения | План состава копии | Отдельные БД и внешние файлы не копируются автоматически |

Сначала проверьте существование исходной БД.
Обычный `sqlite3.connect()` может создать пустую БД при ошибке в пути.
Рецепты чтения ниже открывают источник в режиме read-only.
Для цели используйте новое имя вне рабочей БД.
При ошибке backup не считайте оставшийся целевой файл готовой копией.


## Создать копию через Python

**Ситуация:** нужно скопировать существующий `source.db` в новый `backup.db`.
Фрагмент для Python 3.14 запускается в каталоге учебной исходной БД:

```python
import sqlite3
from contextlib import closing
from pathlib import Path

source_path = Path("source.db").resolve()
target_path = Path("backup.db")
with closing(sqlite3.connect(source_path.as_uri() + "?mode=ro", uri=True, autocommit=True)) as source:
    target_path.touch(exist_ok=False)
    with closing(sqlite3.connect(target_path, autocommit=True)) as target:
        source.backup(target)
```

**Результат:** `backup.db` содержит согласованную копию `main` исходного соединения.
В этом фрагменте занятое имя цели вызывает `FileExistsError` до записи в существующий файл.
Если источник отсутствует, read-only подключение отказывает до создания цели.
Сам `backup()` без этой подготовки может заменить содержимое существующей целевой БД.
Целевой файл после неудачной попытки требует отдельного решения о повторе или удалении.

Для наблюдения за прогрессом используйте callback `progress` у `backup()`.
Параметр `pages` задаёт число страниц за шаг, а не размер всей копии.
[Полный сценарий копии, восстановления и отказов](backup-lab.md#проверить-backup-api)


## Создать копию через CLI

**Ситуация:** нужен файл SQLite без Python.
Фрагмент Bash предполагает существующий `source.db` и свободное имя `backup.db`:

```bash
( set -C; : > backup.db ) && \
sqlite3 -init /dev/null -batch -bail -readonly source.db ".backup backup.db"
```

**Результат:** `.backup` записывает копию в заранее созданный пустой файл.
`set -C` запрещает перенаправлению перезаписать существующую цель.
При занятом имени правая команда после `&&` не запускается.
Если чтение источника или backup отказали, созданный пустой файл может остаться.

`.backup` внутри кавычек — команда CLI, а не SQL.
Без проверки нового имени `.backup` может заменить существующую БД назначения.
`?DB?` в справке `.backup ?DB? FILE` означает необязательное имя БД.
Эта запись не включает показ прогресса.
`-init /dev/null` исключает пользовательский init-файл CLI из учебного запуска.

[Полный CLI-сценарий](backup-lab.md#проверить-cli-копию-и-sql-dump)


## Восстановить копию в новый файл

**Ситуация:** нужно проверить бинарный `backup.db`, сохранив исходную БД.
Бинарная копия уже является файлом SQLite.
Для проверки создайте отдельную рабочую БД.

| Среда | Выбор | Последствие |
| --- | --- | --- |
| Python | Откройте backup read-only; вызовите `backup()` в новую цель | Тот же [фрагмент](#создать-копию-через-python), но источник — `backup.db`, цель — `restored.db` |
| CLI | `.restore backup.db` в новую цель | Заменяет содержимое целевой БД; не направляйте на рабочий файл |

**Пример — фрагмент Bash с проверкой нового имени:**

```bash
( set -C; : > restored.db ) && \
sqlite3 -init /dev/null -batch -bail restored.db ".restore backup.db"
```

**Результат:** `restored.db` содержит снимок из бинарной копии.
Успех команды ещё не подтверждает целостность и нужные данные.
Открывайте только доверенные БД и копии.
Проверьте восстановление до замены рабочего файла.
В рабочем регламенте отдельно определите остановку клиентов и переключение путей.

[Проверки результата](#проверить-восстановленную-бд) · [Полные сценарии](backup-lab.md)


## Создать и восстановить SQL-копию

**Ситуация:** нужен текстовый SQL для просмотра или переноса.
Это альтернатива бинарному backup, а не продолжение `.restore`.
Доверенный источник — `source.db`; имена `dump.sql` и `restored-sql.db` должны быть свободны.

**Пример — фрагмент Bash:**

```bash
( set -C; sqlite3 -init /dev/null -batch -bail -readonly source.db ".dump" > dump.sql ) && \
( set -C; : > restored-sql.db ) && \
sqlite3 -init /dev/null -batch -bail restored-sql.db < dump.sql
```

**Результат:** CLI выполняет SQL в новой БД.
При занятом имени соответствующий шаг останавливается.
SQL dump содержит исполняемый код; восстанавливайте только доверенный файл.
`-bail` останавливает CLI при ошибке, но не делает произвольный SQL атомарным.
Полный `.dump` этой учебной БД содержит границы транзакции.
Неполный dump после ошибки не является готовой копией.
Проверьте схему, данные, индексы и триггеры после восстановления.

[Полный сценарий SQL dump](backup-lab.md#проверить-cli-копию-и-sql-dump)


## Проверить восстановленную БД

**Ситуация:** копия восстановлена в `restored.db`.
Фрагмент SQL выполняется через соединение с этой БД:

```sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;
SELECT id, username FROM users ORDER BY id;
```

**Результат учебного примера:** `integrity_check` возвращает `ok`.
`foreign_key_check` не возвращает строк.
Запрос users возвращает `1 | alice`.
Проверьте результаты явно: сам успешный код CLI не означает, что PRAGMA не обнаружила ошибок.

- [ ] Сравните нужные строки с ожидаемым снимком.
- [ ] Проверьте `integrity_check`.
- [ ] Проверьте `foreign_key_check` отдельно.
- [ ] Проверьте индексы и триггеры.
- [ ] Проверьте ограничения и запросы приложения.
- [ ] Убедитесь, что проверка не изменила рабочую БД.

`integrity_check` проверяет структуру и ряд ограничений, но не проверяет внешние ключи.
Обе PRAGMA не доказывают правильность всех данных и бизнес-правил.
[Полные проверки](backup-lab.md) включают ожидаемые отказы ограничений и поведение триггера.


## Учесть WAL и границы копии

**Ситуация:** исходная БД открыта или работает в WAL.
Используйте согласованную копию через backup API или штатные команды.
Активный `-wal` может содержать существенные данные.
Не копируйте только основной файл активной БД.
Не удаляйте активный `-wal` вручную.

Backup API копирует выбранную БД соединения; по умолчанию это `main`.
Вложенные в приложение внешние файлы и другие attached-БД требуют отдельного плана копирования.
Копия на том же диске не защищает от потери диска.
Режимы шифрования и расширения проверяйте по используемой сборке.

[Практический Python-сценарий](backup-lab.md#проверить-backup-api) копирует открытую WAL-БД без конкурирующего writer.
Для конкурентной нагрузки и сбоев питания подготовьте отдельные сценарии восстановления.
`VACUUM INTO` создаёт отдельную компактную копию; [ограничения](https://www.sqlite.org/lang_vacuum.html#vacuuminto) проверяйте до выбора этого способа.
[Конкуренция и WAL](backup-and-migrations.md#конкуренция-и-wal) описаны отдельно.
