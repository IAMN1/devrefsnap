
# Описание, ревью и проверки PR

[English](../../../en/tools/github-pull-requests/review.md)

Откройте страницу, чтобы описать результат изменения и проверить готовность PR к решению.
Команды создания и смены Draft меняют состояние выбранного репозитория GitHub.

| Задача | Приём | Пример |
| --- | --- | --- |
| Объяснить наблюдаемое изменение | Вход → прежний результат → новый результат | [Описание](#подготовить-понятное-предложение) |
| Создать Draft и проверить цель | Явные base/head и файл описания | [GitHub CLI](#создать-и-посмотреть-через-cli) |
| Разобрать замечания | Разделение действий автора и ревьюера | [Ревью](#действия-автора-и-ревьюера) |
| Проверить готовность к merge | Diff, approvals и обязательные checks | [Перед слиянием](#перед-слиянием) |

Уровень: базовый и средний.
Предпосылки: ветка с изменениями, понимание задачи и правил проекта.
[К справочнику Pull Requests](README.md).


## Подготовить понятное предложение

**Ситуация:** API раньше сохранял пустое имя; теперь должен вернуть `422` до записи данных.
Укажите конкретный вход и наблюдаемое поведение, чтобы ревьюер проверил задачу без переписки.
Сначала проверьте свой diff:

- [ ] Проверьте отсутствие секретов.
- [ ] Проверьте отсутствие отладочных правок.
- [ ] Проверьте отсутствие несвязанных изменений.

PR должен содержать достаточно контекста для человека, не читавшего переписку.
Один связный результат удобнее ревьюить.
Фиксированная граница «до 400 строк» не является правилом GitHub.

Адаптируйте шаблон описания к шаблону конкретного репозитория:

```markdown
## Задача и результат
Что происходило раньше, при каком условии и что теперь меняется.

## Изменения
- Существенные изменения и причина выбранного решения.

## Проверка
- Что выполнено и какой получен результат.
- Что не проверялось и почему это существенно.

## Риски и совместимость
Миграции, несовместимость, ограничения; при необходимости план отката.

## Связанные задачи
Closes #123
```

**Короткий пример — фрагмент описания PR:**

```text
POST /profiles с {"name":" "} раньше сохранял пустое имя.
Теперь API возвращает 422 до сохранения профиля.
Проверка: pytest tests/test_profiles.py — успех и пустое имя проходят.
```

Строка проверки иллюстрирует формат; замените её своей фактически выполненной командой и результатом.
**Результат:** ревьюер понимает, какой запрос проверить и какие данные должны остаться неизменными.
Для UI добавьте сопоставимые снимки до/после.
Для изменения поведения укажите конкретный вход и результат.
Не отмечайте проверки, которые не выполняли.
Фраза «тесты проходят» без команды и контекста мало помогает ревьюеру.
Conventional Commits для заголовка — [соглашение проекта](../git/workflow.md#сообщения-коммитов).


## Создать и посмотреть через CLI

**Ситуация:** ветка `feature/profile` готова к раннему обсуждению; целевая ветка — `main`.
Создайте Draft с явной парой веток и готовым описанием в `pr-body.md`.

Справочные фрагменты предназначены для авторизованного `gh` в правильном репозитории.
Первые команды отправляют ветку и создают объект на GitHub:

```text
git push -u origin feature/profile
gh pr create --draft --base main --head feature/profile --title "feat: add profile" --body-file pr-body.md
gh pr view 123 --web
gh pr list
```

Файл `pr-body.md` должен содержать фактическое описание.
Перед созданием проверьте `git remote -v`.
Проверьте base/head в интерфейсе.
**Результат:** `gh pr create` создаёт Draft PR и выводит его URL.
В следующих командах замените `123` номером созданного PR.
`gh pr view` открывает существующий PR; `gh pr list` показывает список.
Создание требует сети и прав; оно не гарантирует успешный CI или готовность к merge.


## Действия автора и ревьюера

**Ситуация:** PR получил замечания; нужно отделить обязательные исправления от обсуждаемых предложений.
Сопоставьте каждое замечание с целью, поведением и ограничениями проекта.

| Автор | Ревьюер |
| --- | --- |
| Объясните проблему и границы решения | Сверьте изменение с целью и ограничениями |
| Проверьте собственный diff | Проверьте корректность, краевые случаи, безопасность и совместимость |
| Добавьте подходящих ревьюеров | Формулируйте конкретные замечания к коду и поведению |
| Ответьте на замечания. Обоснуйте несогласие | Отличайте обязательное исправление от предложения |
| Отправьте исправления в ту же ветку | Повторно проверьте существенные правки |

Ревью может завершиться Comment, Approve или Request changes.
В зависимости от protections новые коммиты могут потребовать нового approval.
Команда определяет сроки ответа и число ревьюеров.
Универсальное правило «24 часа» или «2+» отсутствует.


## Перед слиянием

- [ ] Проверьте выбор base/head.
- [ ] Просмотрите окончательный diff.
- [ ] Выполните требуемые проверки.
- [ ] Проверьте, что обязательные CI checks относятся к нужному состоянию ветки.
- [ ] Получите необходимые approvals.
- [ ] Обработайте блокирующие обсуждения.
- [ ] Проверьте отсутствие неразрешённых конфликтов.
- [ ] Проверьте, что PR не Draft.
- [ ] Проверьте соблюдение требований репозитория.
- [ ] Выберите согласованную стратегию слияния.
- [ ] Определите последующие действия.

`gh pr checks 123` показывает проверки.
`gh pr ready 123` меняет Draft на готовность к ревью.
Наличие зелёного локального теста не заменяет обязательный серверный check.
