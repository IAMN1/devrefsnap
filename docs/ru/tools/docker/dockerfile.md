# Написать Dockerfile и проверить образ

[English](../../../en/tools/docker/dockerfile.md)

Dockerfile задаёт шаги сборки и команду, которую контейнер выполнит при запуске. Разберите пример сервера, который отдаёт один текстовый файл. Для сборки нужны работающий Docker Engine и базовый образ `python:3.14-slim`. Docker загрузит отсутствующий образ из Docker Hub.

| Задача | Что использовать | Пример |
| --- | --- | --- |
| Написать первый файл | `FROM`, `WORKDIR`, `COPY`, `USER`, `CMD` | [Минимальный сервер](#собрать-первый-образ) |
| Выбрать файлы для сборки | Контекст и `.dockerignore` | [Границы копирования](#выбрать-контекст-сборки) |
| Ускорить повторную сборку приложения | Сначала скопировать список зависимостей | [Установка пакетов](#сохранить-кэш-установки) |
| Выбрать команду или параметр | `RUN`, `CMD`, `ENTRYPOINT`, `ARG`, `ENV` | [Сборка и запуск](#выбрать-инструкцию) |
| Оставить инструменты сборки в отдельной стадии | `FROM … AS` и `COPY --from` | [Стадии сборки](#разделить-сборку-и-запуск) |

## Собрать первый образ

Перейдите из корня репозитория в `examples/tools/docker-basics`. Чтобы повторить пример с нуля, создайте пустой каталог. Поместите в него файл `message.txt` со строкой `Hello from Docker!` и следующий файл с точным именем `Dockerfile`.

```dockerfile
FROM python:3.14-slim

WORKDIR /site
COPY message.txt ./
USER 10001:10001
EXPOSE 8000
STOPSIGNAL SIGINT
CMD ["python", "-m", "http.server", "8000", "--bind", "0.0.0.0"]
```

| Инструкция | Что она меняет в этом примере |
| --- | --- |
| `FROM` | Берёт образ со средой Python 3.14. Тег `3.14-slim` может получить обновления. Чтобы повторно использовать ту же версию базового образа, закрепите его по digest. |
| `WORKDIR` | Создаёт рабочий каталог `/site`, если нужно. Относительные пути назначения и команда контейнера используют этот каталог. |
| `COPY` | Копирует файл из контекста сборки в `/site/message.txt`. Образ содержит снимок файла на момент сборки. |
| `USER` | Задаёт UID и GID процесса. Серверу достаточно читать файлы и слушать порт `8000`. Для записи в каталог ему понадобятся права. |
| `EXPOSE` | Документирует внутренний TCP-порт. Доступ с компьютера задают через `-p` или `ports` в Compose. |
| `STOPSIGNAL` | Задаёт сигнал остановки. Учебный сервер Python обрабатывает SIGINT и завершает работу. |
| `CMD` | Задаёт программу и аргументы по умолчанию. JSON-массив запускает Python напрямую и сохраняет границы аргументов. |

Соберите образ из текущего каталога. Проверьте содержимое до настройки сети.

```bash
docker build -t devrefsnap-web:local .
docker run --rm devrefsnap-web:local cat message.txt
```

Флаг `-t` присваивает образу имя и тег. Команда `cat message.txt` заменяет `CMD` для этого запуска и печатает `Hello from Docker!`. Флаг `--rm` удаляет контейнер после выхода. Образ можно использовать снова. [Полный Dockerfile](../../../../examples/tools/docker-basics/Dockerfile) · [Запуск сервера через Compose](README.md#первый-запуск).

Если хотите проверить сам сервер без Compose, опубликуйте его порт при запуске. Для этого локальный порт `18081` должен быть свободен.

```bash
docker run --rm -p 127.0.0.1:18081:8000 devrefsnap-web:local
```

Откройте `http://127.0.0.1:18081/message.txt` в браузере. Вы увидите ту же строку. Нажмите `Ctrl+C` в терминале сервера, чтобы освободить порт перед запуском через Compose.

Если в `docker build --help` указан параметр `--check`, выполните `docker build --check .` из каталога примера. BuildKit проверит Dockerfile по встроенным правилам. Работу сервера проверяет HTTP-запрос. [Проверки сборки](https://docs.docker.com/build/checks/).

## Выбрать контекст сборки

Последний аргумент `docker build` задаёт **контекст сборки**. В команде `docker build -t devrefsnap-web:local .` точка означает текущий каталог. Исходные пути обычного `COPY` начинаются от корня контекста. Параметр `-f` выбирает Dockerfile отдельно.

Например, из **корня репозитория** та же сборка выглядит так. Обе части пути нужны по разным причинам.

```bash
docker build -t devrefsnap-web:local \
  -f examples/tools/docker-basics/Dockerfile examples/tools/docker-basics
```

Положите `.dockerignore` в корень контекста. В этом примере приложению нужен только `message.txt`. Первая строка исключает файлы из контекста, вторая возвращает нужный файл. Docker всё равно читает Dockerfile и правила исключения для самой сборки. [Полный .dockerignore](../../../../examples/tools/docker-basics/.dockerignore).

```text
*
!message.txt
```

Если добавите `COPY requirements.txt ./`, разрешите и `!requirements.txt`. При ошибке `COPY … not found` проверьте последний аргумент команды, регистр имени и правила исключения. [Контекст сборки](https://docs.docker.com/build/concepts/context/).

## Сохранить кэш установки

Если приложению нужны пакеты, скопируйте список зависимостей перед исходным кодом. Ниже фрагмент Dockerfile приложения с PostgreSQL после `WORKDIR /app`. Для этого приложения в контексте нужны все три указанных файла. [Полный Dockerfile с Psycopg](../../../../examples/tools/compose-and-github-actions/Dockerfile).

```dockerfile
COPY requirements.txt ./
RUN python -m pip install --no-cache-dir -r requirements.txt
COPY app.py test_app.py ./
```

Если изменился только `app.py`, Docker может повторно использовать результат установки. Изменение `requirements.txt` приводит к повторной установке. Флаг `--no-cache-dir` относится к внутреннему кэшу pip. Кэш шагов Docker действует отдельно. [Порядок слоёв и кэш Docker](https://docs.docker.com/build/cache/optimize/).

## Выбрать инструкцию

| Что требуется | Пример | Когда действует |
| --- | --- | --- |
| Установить пакет в образ | `RUN python -m pip install -r requirements.txt` | При сборке, если шаг не взят из кэша |
| Задать заменяемую команду | `CMD ["python", "app.py"]` | При создании контейнера без своей команды |
| Сохранить исполняемую программу при замене аргументов | `ENTRYPOINT ["python", "-m", "http.server"]` вместе с `CMD ["8000"]` | В таком образе аргумент `9000` после имени образа запускает сервер на порту 9000 |
| Выбрать базовый образ при сборке | `ARG PYTHON_VERSION=3.14` перед `FROM python:${PYTHON_VERSION}-slim` | Значение можно передать через `docker build --build-arg PYTHON_VERSION=3.14 .` |
| Задать настройку процесса по умолчанию | `ENV PYTHONUNBUFFERED=1` | Значение входит в образ. Сервис Compose может заменить его через `environment`. |

В exec-форме `CMD` и `ENTRYPOINT` оболочка не подставляет `$VAR`. Для секретов сборки используйте secret mount BuildKit. Значения `ARG` и `ENV` могут попасть в образ или метаданные сборки. [Инструкции Dockerfile](https://docs.docker.com/reference/dockerfile/) · [Секреты сборки](https://docs.docker.com/build/building/secrets/).

## Разделить сборку и запуск

Если для получения артефакта нужен компилятор или установщик, дайте стадии сборки имя через `FROM … AS builder`. Начните следующую стадию с нового `FROM`. Перенесите в неё нужный результат. Ниже фрагмент финальной стадии примера с uv.

```dockerfile
COPY --from=builder /app/.venv /app/.venv
```

Здесь путь источника начинается от корня файловой системы стадии `builder`. Для переноса такой среды Python нужны совместимые базовые образы и одинаковый путь установки. Если одному проекту нужны разные конечные образы, сервис Compose может выбрать стадию через `build.target`. [Полный пример с uv](../../python/tooling/uv/automation.md#docker) · [Выбор стадии в Compose](compose-file.md#указать-dockerfile) · [Многостадийная сборка](https://docs.docker.com/build/building/multi-stage/).
